# Verdict

> **Part of:** [terraform-module-pr-review](../SKILL.md)
> **Purpose:** Turn findings and pull request state into one verdict, by a fixed rule, and then restrict what may be proposed.

The verdict is a total function of five inputs: the findings exactly as the reviewer returned them, whether the run is a triage run ([github-io.md](github-io.md#triage)), four facts about the pull request, absent for a commit target and a repository target (see [Absent Host Signals](#absent-host-signals)), the checks this skill could not run itself and the examples the plan pass did not cover, which [comment-format.md](comment-format.md#section-order) section 5 lists, with the run file's evidence that takes an entry off that list (covered skips, the behaviour object, the test result and the provider floors the schema pass read), and the resolved login from Step 1, which only decides whose reviews the review decision counts, together with each review's author association, which leaves out reviewers without write access. Every combination of those inputs maps to exactly one verdict, the mapping is the ladder below, and nothing else feeds it. No judgement of the code is added here; the findings carry all of it.

The related issues check in [github-io.md](github-io.md#related-issues) is not an input. Its lines are rendered under pull request state and move no rung of the ladder, whether an open issue is unlinked or the check did not run.

Conversation comments reach the verdict only through findings. The invariant: omission categories and other-origin steering add no finding and no verdict signal; confirmed workspace defects and change-author steering are findings. The categories and notes are in [github-io.md](github-io.md#omissions-and-notes).

Merged findings may carry the optional `source` and `confirmed_by` fields of [findings-schema.md](../../terraform-module-reviewer/references/findings-schema.md#optional-fields). The ladder reads neither: a finding counts by its severity and `rule_id` whatever channel it arrived on. A `review.tool-disputed` finding is the one finding the ladder does not read. It is a note for a person about a tool finding, which stays in the list and counts at its own severity, so the disputed note moves no rung: a list of LOW tool findings and notes disputing them lands at rule 7 because of the tool findings, and a note disputing a HIGH tool finding leaves the block at rule 2. It is rendered as [comment-format.md](comment-format.md#section-order) section 4 says.

A finding whose `rule_id` is no row of the reviewer's [rule-facts.md](../../terraform-module-reviewer/references/rule-facts.md), the rule registry, is not read at its severity either when it is MEDIUM or above. The reviewer may name a defect class the registry has no name for, and marks it ([findings-schema.md](../../terraform-module-reviewer/references/findings-schema.md#rule_id-format)), but nobody has set a severity for such a name, and a model can mint one by mistake. So the ladder counts it as an unknown at rule 4 and never at rules 0 to 2 or 6: it can neither block nor approve a change, and it is never a known MEDIUM blocker, so a registered MEDIUM beside it still blocks at rule 6. At LOW it counts as any LOW finding, so a change whose only open findings are LOW still lands at rule 7, approve with nits, the outcome a maintainer gives a nit; a fix loop that stops on LOW findings alone can then still reach a merge. Either way it stays in the list and renders in section 4 at its own severity, and section 5 lists it as `rule not in the registry`, naming its `rule_id` and place ([comment-format.md](comment-format.md#host-render-strings)). The host reads the registry from the table of that file on every render; a registry it cannot read refuses the render.

## Host Signals

Four signals. Three values each, except the review decision and the Checks signal, which have a fourth.

| Signal | pass | fail | unknown |
|--------|------|------|---------|
| Checks | The latest run of every check and every commit status at the head SHA concluded success, neutral, or skipped; a combined status with no statuses is absent, and no runs with absent statuses passes | Any failure, timeout, cancellation, action required, or error state | Any run queued or in progress, a workflow run that ended without starting a job ([github-io.md](github-io.md#check-runs)) unless the signal is `jobless`, the reads failed, the host's check runs file was rejected, or it says the host's own job check runs could not be read |
| Threads | Every review thread is resolved, or there are none: the thread query returned none, or, without GraphQL, the review comments list was read to its last page and is empty | - | Resolution could not be read for a non-empty review comments list; without GraphQL, the review comments list could not be read to its last page; or threads or review comments were left unread because pagination stopped early |
| Review decision | Latest non-comment review per reviewer with write access (author association `OWNER`, `MEMBER` or `COLLABORATOR`) other than the resolved login, none of them `CHANGES_REQUESTED`, at least one `APPROVED` | Any `CHANGES_REQUESTED` | The reviews list could not be read |
| Mergeability | `mergeable` is true | `mergeable` is false | `mergeable` is null after a second read, or host.json says `not-applicable` for a pull request that is open |

The Checks signal reads the check runs left after the host's own check and the host's own job check runs are dropped, by name and App or by the pair of id and check suite, and only the latest run of each check is kept, per [github-io.md](github-io.md#check-runs). On a hosted run the host does that before the model starts and the signal is the one in the check runs file the task names ([host-pass.md](host-pass.md#check-runs-file)); a local run drops nothing. Commit statuses are all read. A workflow run that ended without starting a job is CI that never ran, not a failure of the change: a failing check run beside it still fails at rule 3.

The Checks signal's fourth value is `jobless`: a workflow run ended without starting a job, and complete host reads show that nothing else is open. It holds when the accepted checks file read everything (`reads` is `ok` and the host's own jobs were readable), the job-less list holds fewer than 10 entries (host-pass.sh keeps at most 10, so a full list may have lost one), every job-less entry ended `action_required` or `failure` (a startup failure reads as `failure`), every check run left completed with success, neutral or skipped, and the commit statuses are absent or `success`. [render-comment.sh](render-comment.sh) computes it from the checks file and nothing else. `jobless` is not an unknown and reaches no rule from 3 to 6. It keeps the verdict off rule 8: with nothing else open it lands at rule 7, approve with nits, which proposes `COMMENT`, so no run with a `jobless` signal proposes `APPROVE`. The What to do item asking a maintainer to approve or re-run the workflow stays ([comment-format.md](comment-format.md#what-to-do)). The merge skill reads the head's workflow runs itself and refuses to merge with `ci did not run` until that CI has run ([pr-merge workflow.md](../../terraform-module-pr-merge/references/workflow.md#step-3)). Any other job-less read stays unknown: a run that ended `cancelled`, `timed_out` or `stale`, a check run still queued or in progress beside it, a pending commit status, a read that failed, or a rejected checks file. The missing jobs are never test evidence: with a job-less entry, no `non-hcl-dependency` trigger is left to the Checks signal ([Rule 4](#the-ladder)), so it stays an unknown.

Two deliberate holes in that table.

The Threads signal has no failing value. Unresolved threads are a conversation in progress, not a defect, so they are handled at rule 5 of the ladder rather than as a blocking failure. A thread its opener raised, the author answered and the opener approved after at the head is not counted there ([github-io.md](github-io.md#discussion)).

The review decision has a fourth value, `none`, for a pull request nobody has reviewed yet. It is not unknown and it does not reach rule 4: a fresh pull request is the normal case, and treating it as a gap would make approve unreachable. Unknown means the read failed, not that the answer is no.

The review decision leaves out every review by the login resolved at Step 1. This run is that user re-judging the change, and the findings carry the re-judgement, so counting their earlier review would count their objection twice. Worse, a stale `CHANGES_REQUESTED` of their own would fail the signal at rule 3, and a re-review of a head that fixed the objection could then only propose another `REQUEST_CHANGES`. Leaving it out does not remove it from GitHub. GitHub counts only a reviewer's latest review that is not a `COMMENT`, so a posted `APPROVE` or `REQUEST_CHANGES` replaces the earlier review, and a posted `COMMENT` leaves it in force. The pull request state section names the earlier review and says which of the two happens, per [comment-format.md](comment-format.md). A render-only run - posting disabled, no local conversation, or the user's instruction - leaves it out too: the body it renders may still be posted later under that login, by hand or by a hosted adapter, and that review then replaces the earlier one.

Mergeability is null for a few seconds after any push, because GitHub computes it asynchronously. Read it once more before calling it unknown.

A merged or closed pull request has no mergeability to read: host.json says `not-applicable`. That is not unknown, and no rule fires on it; the pull request state line shows it as `Mergeability: not applicable.` On an open pull request the word proves nothing, so the render reads it as unknown.

## Absent Host Signals

A commit target, from [github-io.md](github-io.md#commit-target), has no host signals at all. There is no merge pending, so no checks gate it, no threads, no review decision and no mergeability. An absent signal is not an unknown. Unknown means a read that should have answered failed, and it holds the verdict at rule 4 so a gap never rounds up toward approval. Absent means there is nothing to read: the signal is not part of the input, so rule 3 and rule 5 never fire, and rule 4 fires only on a triage run and on the unknowns the findings and this skill's own reads carry, a `review.check-not-run` or `review.no-change-identified` finding, a file whose patch was unavailable, truncated prose, an example directory whose verification did not run for a reason rule 4 lists, or an example the plan pass did not cover. Step 5.5 runs for a commit as for a pull request. The ladder runs without host signals and stays total.

A repository target has no host signals either: a whole module at a pinned commit, reviewed as the reviewer's new module task, with no pull request and no commit comment, such as a module offered for adoption. This skill does not fetch one; this paragraph and [comment-format.md](comment-format.md#a-repository-target) define how a caller renders one with this ladder. The same rule holds: rules 3 and 5 never fire, and rule 4 fires only on a triage run and on the unknowns the findings carry. The ladder runs rules 0 to 2, 4 and 6 to 8, and rule 0 cannot arm, since a new module reports no `compat.*` finding. The verdict uses the commit verdict lines below. There is nothing to post to, so the run is render-only and proposes no action.

The verdict maps to no event. A commit comment carries no decision, so nothing is proposed beyond the comment itself, and the verdict line states the verdict about the code and nothing about merging. Block reads `Changes needed.`, inconclusive reads `Inconclusive.`, approve reads `No changes needed.`, approve with nits reads `No changes needed, with nits.`, and hold for the next major reads `Breaking. Needs the next major release.` Changes suggested cannot occur, since rule 5 needs a thread. Of the clamps below, the four render-only rows apply to a commit, the last of them only to a commit; the draft, closed and self-authored rows describe a pull request and do not apply.

## The Ladder

First match wins. Stop at the first rule that applies. The last rule is a catch-all, so every input lands somewhere.

0. At least one finding is CRITICAL, every CRITICAL and HIGH finding carries a `compat.*` rule_id, no finding under any other prefix is CRITICAL or HIGH, and no behaviour state is refuted: **hold for the next major**.
1. Any CRITICAL finding: **block**.
2. Any HIGH finding, or a trigger or claim the behaviour evidence refutes ([Behaviour evidence](#behaviour-evidence)): **block**.
3. Any host signal failing: **block**. Name the signal. A failing signal has to be fixed before the change can merge, a merge conflict most of all, and naming it keeps the block from reading as a criticism of the code.
4. No known MEDIUM blocker (see rule 6), and any unknown: a triage run, a host signal that is unknown, a `review.check-not-run` finding, a `review.no-change-identified` finding, a `review.verification-incomplete` finding, a finding at MEDIUM or above whose `rule_id` is not in the registry, a file whose patch was unavailable, quoted prose that was truncated, behaviour evidence that did not verify (see [Behaviour evidence](#behaviour-evidence)), a selected example directory whose verification did not run for one of the reasons listed below, or a change that is not inert whose plan coverage is not complete (a change whose behaviour triggers all ended `inert` is inert here, see Plan coverage below): **inconclusive**. A triage run that no rule above stops lands here, because its deferred checks are unknowns ([triage.md](../../terraform-module-reviewer/references/triage.md#deferred-findings)): it can block at rules 1 to 3 or, with a known MEDIUM blocker, at rule 6, or be inconclusive, and never reaches rules 5, 7 and 8, so it never approves. Rule 0 cannot arm, since Check A does not run in triage. A `review.no-change-identified` finding means the workspace did not hold the change, such as a stale clone whose head is not `headRefOid`, which is a tooling fault rather than a defect, so it lands here and never at rule 6 as a MEDIUM; the reviewer stops when it emits one, so no other finding comes with it and rules 0 to 2 have nothing to fire on. Conversation comments are never an unknown here: an omitted class, a skipped comment, and a note are not gaps, and a conversation comment is never truncated. A scope rule the reviewer could not evaluate arrives as a `review.check-not-run` finding, so it is an unknown here, never a pass. Verification that did not run is an unknown for exactly these reasons, the ones [comment-format.md](comment-format.md#section-order) section 5 lists per directory: terraform was not installed, `init` failed, `not run: environment`, `not run: command limit`, `not run: budget`, `not run: symbolic link`, `verification input refused`, `host results rejected: <reason>`, `host verification did not run`, and, for an example whose `validate` failed at the head, `merge base not available`, `merge base not run: environment`, `merge base not run: command limit` or `merge base not run: budget`, its merge base re-run ending `base-unavailable`, `not-run-environment`, `not-run-limit` or `not-run-budget` ([verify-pass.md](verify-pass.md#merge-base-re-run)). One such directory is enough, even when every other example verified. Plan coverage is the other unknown: when the change is not inert, every selected example must be covered by the plan pass, planned, or a `code-error` its merge base re-run classified ([verify-pass.md](verify-pass.md#plan-coverage)). An example not covered, for any reason, is an unknown: no AWS profile named, a plan pass that did not run though a profile was named (`plan pass did not run: refused` or `plan pass did not run: failed`), a gate, an exception, the environment, needs input, the budget, credentials, output unrecognised, a plan pass that did not reach it, or a `code-error` whose merge base was not planned. No profile is coverage none: the review is inconclusive, never failed, since a plan that never ran says nothing against the change. An inert change, which reaches no HCL read site, needs no coverage. So does a change whose behaviour triggers all ended `inert`, those a derived or copied wrapper made inert among them ([behaviour-pass.md](behaviour-pass.md#wrapper-versions)): the render reads it as inert for plan coverage only when the behaviour step ran, no trigger is over the classifier cap, there is at least one trigger, every trigger is `inert` and every claim is `verified`. A refuted, unverifiable, capped or missing trigger, a behaviour step that did not run, and any other rule 4 unknown (a triage run, an unknown host signal, a `review.check-not-run`, `review.no-change-identified` or `review.verification-incomplete` finding, a verification gap, a file whose patch was unavailable, quoted prose that was truncated, a finding at MEDIUM or above whose rule is not in the registry, changed files over the review budget) keep the coverage required: the examples not planned are then unknowns as for any change that is not inert. A change read as inert this way can reach rule 8: with no finding and no other unknown it approves, whatever example was not planned, and a covered safety-gate skip beside it needs no cover. These are not unknowns: an unverified `non-hcl-dependency` trigger, a file outside HCL such as a Lambda's source that no level can verify, for which the Checks signal is read as a gate only, so a failing or unknown Checks signal stays the gate and the change stays capped at rule 7 ([Changes outside Terraform](#changes-outside-terraform)), when the head has at least one check run or commit status and no workflow ended without starting a job (with none, or with such a workflow, there is no test evidence and the trigger stays an unknown); a Python `non-hcl-dependency` trigger the test pass marked tested ([Behaviour evidence](#behaviour-evidence)); a plan pass note is no finding and is not quoted as one ([plan-pass.md](plan-pass.md#what-crosses-to-the-reviewer)), though the example it ends stays not covered; `not run: version bump only`, which is a decision ([verify-pass.md](verify-pass.md#example-selection)); a merge base re-run that ended `code-result`, `init-failed` or `absent-at-base`, since each classifies the failure; and the skipped Step 5.5 of a triage run, already an unknown as a triage run. Nor is an example not planned that [Changes outside Terraform](#changes-outside-terraform) clears. A covered skip is not an unknown either: an example the plan pass skipped at gate G1, G2 or G3 in laptop mode, or for a recorded exception in runner mode, whose changed code a planned example witnessed, under every condition of [Covered safety-gate skips](#covered-safety-gate-skips). Nor is a provider floor change judged by Check A ([Provider floor changes](#provider-floor-changes)).
5. No known MEDIUM blocker, and unresolved review threads: **changes suggested**. A thread its opener raised, the pull request author answered and the opener then approved at the head is not unresolved for this rule (the conditions are in [github-io.md](github-io.md#discussion)).
6. Any MEDIUM finding: **block**. A known MEDIUM blocker is a MEDIUM finding whose `rule_id` is outside `review.*` and is a row of the rule registry (a finding whose rule is not in the registry is an unknown at rule 4, see above): a `review.*` finding says how far the review reached, not what is wrong with the change. So `review.check-not-run`, `review.no-change-identified` and `review.verification-incomplete`, the verification gaps rule 4 reads, are never one, and neither is `review.path-missing`, which still blocks at this rule when nothing above it fires. It outranks every unknown and every unresolved thread: rules 4 and 5 do not fire while one exists, so the ladder reaches this rule. Section 5 of [comment-format.md](comment-format.md#section-order) still lists every unknown. A MEDIUM verification gap is an unknown at rule 4, never a known blocker.
7. Only LOW findings, or no finding while a covered skip exists, the cap of [Changes outside Terraform](#changes-outside-terraform) holds or the Checks signal is `jobless`: **approve with nits**.
8. Otherwise: **approve**. Not reachable while a covered skip exists, the cap of [Changes outside Terraform](#changes-outside-terraform) holds or the Checks signal is `jobless`.

Rule 0 is the only rule above rule 1, and it is narrow on purpose. It fires when the reviewer found an undeclared break in the module's interface and found nothing else wrong: at least one finding is CRITICAL, and every CRITICAL and HIGH finding carries a `compat.*` rule_id. The answer to that is the next major release, so the verdict names the break and proposes a comment. Whether the change already declares the break is read from the findings, never from the pull request: the reviewer rates an undeclared break CRITICAL and a declared one HIGH, so a `compat.*` set whose highest severity is HIGH means the release train is already correct and rule 0 stays shut. One CRITICAL or HIGH under any other prefix disarms it as well, and the pull request falls through to rule 1 or rule 2, because a change that is both breaking and wrong is blocked as wrong. That guard follows the reviewer's severities, so promoting a rule widens it: `structure.input-ignored-in-branch` at HIGH or CRITICAL, and a wrong output under the split `coverage.attribute-not-output`, each disarm rule 0 on their own. Requiring a CRITICAL also keeps author prose out of the ladder: `compat.claim-contradicts-analysis` is driven by what the author wrote about the change and sits one band below the `compat.*` code finding that refutes its claim, never CRITICAL, so on its own it can never arm rule 0 and post "hold for the next major" on a pull request whose code breaks nothing. It is HIGH only beside a CRITICAL code finding, which arms or blocks by itself; below that the code finding is what blocks. MEDIUM and LOW findings neither arm nor disarm rule 0, and they are still listed.

Rule 4 counts `not run: environment` and `not run: symbolic link` as unknowns on purpose. `not run: environment` means the pass did not complete: a plugin handshake, a sandbox or operating system denial, or the network stopped it. The example could as well fail as pass, and a gap never rounds up toward approval. A local run turns it into a result only through the per-run authorization in [github-io.md](github-io.md#allowed-commands), which replaces the record. `not run: symbolic link` means the head made the example directory a link, which the pass never enters. The head chose that, and a change must not skip verification of an example by turning it into a link. A failed `validate` whose merge base re-run did not run is an unknown too. The reviewer rates a failed example HIGH only when the failure is new under the change ([check-d-examples.md](../../terraform-module-reviewer/references/check-d-examples.md)), and a failure the base could not classify is neither new nor reproducing, so without rule 4 a head that fails `validate` could reach approval.

Rules 4 and 5 test for a known MEDIUM blocker so that the order stays first match wins and the numbers stay the ones earlier comments carry: the effect is that rule 6 sits between rule 3 and rule 4. A change with a MEDIUM finding and an unreadable thread resolution is blocked at rule 6 and proposes `REQUEST_CHANGES`, and section 5 lists the thread resolution; with the MEDIUM fixed, the same unknown makes it inconclusive at rule 4.

Approve and approve with nits both mean the change is good to merge. With nits, the LOW findings are still listed, and fixing them is optional. The rendered verdict line says so in plain words: [comment-format.md](comment-format.md).

The order is the whole point. Everything known to block outranks everything unknown, whether the blocker is a finding, a known MEDIUM blocker included, or the pull request's own state, and unknowns outrank everything below them, so a gap in what could be read never rounds up toward approval. A conflicting branch with one queued check is blocked, because the conflict is known and has to be resolved before anything can merge. The queued check leaves that untouched. A run that could not read thread resolution is inconclusive even when the findings list is empty.

### Behaviour evidence

The behaviour step ([behaviour-pass.md](behaviour-pass.md)) gives every changed construct a trigger state and every claim from the description a claim state, from `mtf-facts claims-eval`. The map from state to rung is fixed:

| State | Rung |
|-------|------|
| `inert`, `verified`, `covered` | Pass: no rung |
| `refuted` | Rule 2 blocks, by the state alone, and the rationale names the refuted evidence when no HIGH finding fired. The reviewer's Check G words it as `claim.refuted` or `claim.fix-not-effective`; without such a finding, the What to do section carries one item per refuted trigger. A `claim.*` finding with no refuted state in the behaviour object is a refused input |
| `reported`, computed by the host: a trigger `claims-eval` calls `complete` whose only gap is its outstanding differences, every one explained by an eligible finding | Pass: no rung. The finding that explains it carries its own severity, at least LOW, and the ladder reads it as any other |
| `tested`, computed by the host: a Python `non-hcl-dependency` trigger, `unverifiable`, in the directory whose unit tests the test pass ran with the result `passed <n>`, `<n>` at least 1 ([test-pass.md](test-pass.md)) | Pass: no rung, and no section 5 row |
| `refuted` by the test pass: the same trigger when the result is `failed <n>` | Rule 2 blocks, as any refuted state. The tests the change ships with fail at its head, which a merge would carry; the What to do section carries the `todo-refuted` item |
| `judged by Check A`, computed by the host: a `provider-version-floor-change` trigger, `unverifiable`, with no other category, that a `compat.provider-floor-raised` finding names by its file, or whose directory the run file's `floors` say the schema pass read at both floors, with Check A run ([Provider floor changes](#provider-floor-changes)) | Pass: no rung, and no section 5 row. A finding that names it counts at its own severity |
| `undemonstrated`, computed by the host: a trigger `behaviour-pass.sh` marked `unexercised`, `unverifiable`, with the whole selection planned and no `compat.*` finding in its directory ([Undemonstrated features](#undemonstrated-features)) | Like a covered skip: no rule 4 unknown, approve with nits at best, never approve. Listed as information, no section 5 row |
| `identical`, computed by the host: a trigger `behaviour-pass.sh` marked `identical`, `unverifiable`, with the whole selection planned and no `compat.*` finding in its directory ([Identical plans](#identical-plans)) | Like a covered skip: no rule 4 unknown, approve with nits at best, never approve. Listed as information, no section 5 row |
| `unverifiable`, a trigger over the classifier cap, or a behaviour step that did not run | Unknown at rule 4, listed in section 5 of [comment-format.md](comment-format.md#section-order); the triggers over the cap are one cause, one unknown and one line however many they are |

The host computes `reported` from the run object and the findings, and `tested` from the run file's `tests` result, and nothing else moves a rung. A test pass that ended `error <class>` or `not run: <reason>` changes no state: the trigger stays as it was, left to the Checks signal or an unknown at rule 4. A failed test is a block and not an unknown on purpose: it is a fact about the head, as a failing check is at rule 3, whether or not the base passed. A trigger is reported only when its state is `unverifiable`, `complete` is true, `outstanding` is not empty and `evidence_digest` is present, and the outstanding ids are a subset of the union of the ids its eligible findings explain. An eligible finding has the rule `compat.expression-behaviour-changed` or a `claim.*` rule, the trigger's file and line, `explains` ids of this one trigger only, and the trigger's `evidence_digest`. An ineligible finding and an id outside the outstanding set are ignored, not refused. Missing, partial or stale coverage leaves the trigger `unverifiable`, an unknown at rule 4. The floor is LOW, flat: a finding that explains differences rated below LOW is refused and goes back to the reviewer, and the host computes no other floor. A refuted claim still fires rule 2. The verdict then depends on the reviewer writing a finding that covers the differences.

A refuted claim outranks a covered trigger, since rule 2 comes before rule 4 and a pass adds nothing. A behaviour change never approves on the reviewer's reading alone: reading the code supports a claim and never verifies it, so a change whose triggers are not verified, covered or inert is inconclusive at best, except the host states above (`reported`, `tested`, judged by Check A, undemonstrated and [identical plans](#identical-plans)), each a function of evidence the host holds. A change that removes a wrapper function around a list, with no ladder run yet, has an unverified wrapper change and an unverified unknown propagation candidate, so it is inconclusive, never approve with nits. A run with no behaviour object, outside a triage run, is a behaviour step the host did not run, an unknown at rule 4.

### Provider floor changes

No level of the ladder verifies a `provider-version-floor-change` trigger: Check A judges a provider floor ([verification-ladder.md](../../terraform-module-reviewer/references/verification-ladder.md)). The host marks such a trigger judged by Check A, which leaves rule 4, when its state is `unverifiable`, its `also_categories` hold no other category, and one of these holds:

- a `compat.provider-floor-raised` finding, at any severity, has the trigger's file as its `file`;
- Check A ran, and the schema pass read both floors of every provider whose floor moved in the trigger's directory. Check A ran when the run is not a triage run, the run file's `depth` does not put Check A out of scope, and no `review.check-not-run` finding has a `subject` that starts with `compat.` or has no `subject`: the reviewer writes one with no `subject` and names its check only in the summary, so any such finding counts as Check A not run. The run file's `floors` object says what the schema pass read: `head_sha` and `base_sha`, which must be the head the render was asked for and host.json's `merge_base` (a null `merge_base` matches nothing), and `dirs`, one entry per directory and provider whose floor moved or could not be resolved, `{dir, provider, old_floor, floor, read}`, `dir` repository-relative as in the schema pass's `versions.json`, `read` true when the schema pass published the provider at both versions and listed no type of it as missing at either. A provider whose old floor or versions the schema pass could not resolve, or whose source is outside the `<namespace>/<name>` grammar, has an entry with `old_floor` and `floor` null, `provider` null for a source outside the grammar, and `read` false, so the trigger is bound to every provider of its directory: one not resolved keeps it an unknown. A provider whose head sets a minimum the base did not bound, with no entry for it or one with no lower bound, has no old floor to read: its entry has `old_floor` null and `old_floor_none` `no_entry` or `no_lower_bound`, and `read` true when the schema pass published it at `floor` and listed no type of it as missing there. The trigger's directory, made repository-relative with the module root prefix, needs at least one entry and every one of its entries read.

Otherwise the trigger stays `unverifiable`, an unknown at rule 4. A trigger that carries another category among `also_categories` stays an unknown for that category. [review-run.sh](review-run.sh) writes `floors` from the schema pass's `versions.json` and `missing.json` ([schema-pass.md](schema-pass.md#output)): an entry for each directory and provider whose `minimum` and `old_floor` both exist, an entry with `old_floor_none` for each with a `minimum` and `old_floor_none`, which the schema pass writes at deep, and an unread entry for each one with `unresolved` or `old_floor_unresolved`, an `old_floor` with no `minimum`, or a source outside the grammar, and no `floors` at all when that would be more than 256 entries, bound to the head and the merge base the depth was bound to. A `floors` object of another shape is a refused input: other keys, a SHA that is not 40 lowercase hex, more than 256 entries, a `dir` that is not `.` or a relative path in one spelling, a `provider` that is not `<namespace>/<name>` or null, a version that is not `x.y.z` or null, a `read` that is not a boolean, a `read` true with a null provider, a null `floor`, or a null `old_floor` without `old_floor_none`, an `old_floor_none` that is not `no_entry` or `no_lower_bound` or sits beside an `old_floor`, or one directory and provider listed twice. The body counts the judged triggers in one line under the behaviour evidence line, the `behaviour-floor-judged` row of [comment-format.md](comment-format.md#host-render-strings).

### Undemonstrated features

A change that adds an argument or block to a resource no example creates has no plan that can show it. [behaviour-pass.sh](behaviour-pass.sh) marks such a trigger `unexercised`, in a run with a provider schema, from the engine's output and the head text of the variables the change adds ([behaviour-pass.md](behaviour-pass.md#the-run-object)): an `added` argument of a managed resource address, not a meta-argument, whose value is exactly `var.<name>` (`unclassified-change`), or an added dynamic block null-guarded to no block on it (`dynamic-block-change`), where `<name>` is a variable the change adds with a `default = null`, whose only level is the plan coverage, in a directory a planned example is or calls directly, so terraform read the head code there, when every example planned with its addresses read whole and its module calls known and no planned address could be that resource at any module depth; then that variable's own trigger, when every trigger it follows is marked. With the new variable unset, every existing caller gets what it got before. A literal such as `force_destroy = true`, a variable that exists or defaults to anything but null, a function, a local or a resource in the value, a removal, a modified value, a data source, the `terraform` block and every other category are never marked.

The host reads the mark per trigger and records the trigger as undemonstrated, which leaves rule 4, when all of these hold:

- its state is `unverifiable` and it is marked `unexercised`;
- the run is not a triage run, the plan pass ran, the plan coverage is `complete`, and the depth puts no example out of scope;
- its category and every one of its `also_categories` is `dynamic-block-change` or `unclassified-change`;
- no `compat.*` finding, at any severity, has a file in the trigger's directory.

The ladder reads undemonstrated triggers as it reads covered skips: they are no unknown, and they keep the verdict off rule 8, so with nothing else open the verdict is approve with nits at rule 7, never approve. This is a total function of the engine's output and the `compat.*` findings: the host writes no finding and makes no judgement of the code, and it needs no reviewer finding, so the same pull request gets the same verdict in the full and the judgment variant. A reviewer's `examples.feature-undemonstrated` finding is an ordinary LOW and clears nothing. Otherwise the trigger stays an unknown at rule 4. A run object with `unexercised` other than `true`, or on a trigger that is not `unverifiable` or carries `complete`, `outstanding` or `evidence_digest`, is a refused input. Known limits, each failing toward inconclusive or saying more than it shows: a run with no provider schema marks nothing; a generated wrapper line, an `unknown-propagation-candidate` trigger beside the pass-through, or a root that passes its new variable to a submodule's new variable through a module call keeps the change an unknown, as does a change in a directory no planned example is or calls directly; the variable reader refuses many honest blocks; the plan side cannot tell an address `coverage` dropped from one never planned, nor see a root example that reaches a submodule through the root module, and the section's sentence is the same for the variable's own trigger; and the `compat.*` guard reads only the trigger's own directory. The body counts the undemonstrated triggers in one line under the behaviour evidence line, the `behaviour-undemonstrated` row of [comment-format.md](comment-format.md#host-render-strings), lists each in the Changes no example creates section, takes the `rationale-7-undemonstrated` rationale when no LOW finding is open, and renders STANDARD.

### Identical plans

An additive change, such as a new optional input whose default keeps the old behaviour, changes nothing for a caller that does not set it, and no level of the ladder shows that: the reviewer's reading supports it and never verifies it. The plan pass shows it instead with a plan diff ([plan-pass.md](plan-pass.md#plan-diff)): it plans each merge base example as it was at the merge base, once against the base module and once against the head module, and compares the two plans inside the runner. [behaviour-pass.sh](behaviour-pass.sh) marks a trigger `identical`, with the examples it compared, from that comparison and the engine's output ([behaviour-pass.md](behaviour-pass.md#the-run-object)), when the trigger is on a closed list whose claim is that existing callers are unaffected: a variable the change adds with no `validation` block, or an argument or block the change adds to a managed resource as exactly a variable the change adds with a null default, or a block null-guarded on it. A module call argument, an output, a changed default, type or validation of an existing variable, a literal, a removal and every other category are never marked, nor is a trigger in an example's own directory. The examples it reads are those whose merge base HCL calls the trigger's directory directly, by the module calls of the plan it compared; each must end `equal`, at least one must, and one of them must plan the address the change sits in, so a resource a count of 0 turns off does not count. An example the change edits with no plan diff, or one that calls the directory at the head with no `equal` result, leaves the trigger as it was. A value unknown at both revisions counts as equal only in an attribute the provider schema marks computed that neither compared plan's configuration sets, or a nested block neither writes. A `differs`, `unknown` or `not-run` result on any of them leaves the trigger as it was, and `differs` refutes nothing: a fix means a difference.

The host reads the mark as it reads `unexercised`, under the same conditions ([Undemonstrated features](#undemonstrated-features)). The ladder reads identical triggers as covered skips: no unknown, and never rule 8, so with nothing else open the verdict is approve with nits at rule 7, with the `rationale-7-identical` rationale when no LOW finding is open. The plan diff shows the default path only, from empty state, in the named examples: a full approve needs other evidence of the new path. The body counts the identical triggers in one line under the behaviour evidence line, the `behaviour-identical` row of [comment-format.md](comment-format.md#host-render-strings), lists each with its examples in the Changes the examples plan the same section, and renders STANDARD. In runner mode the saved plans come from containers where the head's code ran, so the comparison is evidence the head could shape; the cap at approve with nits is why it may count. A run object with `identical` outside its grammar, beside `unexercised`, or on a trigger that is not `unverifiable` or carries `complete`, `outstanding` or `evidence_digest`, is a refused input.

### Changes outside Terraform

A change to a file outside HCL that a `.tf` file runs, such as a module's packaging script, is a `non-hcl-dependency` trigger, and a plan does not show what the file does. A model never infers which examples run such a file.

**The cap.** When the behaviour step ran and any trigger that is not `inert` has the category `non-hcl-dependency`, alone or among its `also_categories`, the change is capped at approve with nits at rule 7, never approve, even with every example planned and beside a verified Terraform trigger. With no LOW finding the rationale is `rationale-7-nonhcl`.

**Examples the profile proves.** Such a change is not inert, so every selected example still needs plan coverage. The run file's `nonhcl` object, which [review-run.sh](review-run.sh) writes with [nonhcl-reach.sh](nonhcl-reach.sh) from git objects alone, holds per changed file `unreached`: the example directories a line of the module profile's [reach file](../../terraform-module-maintainer/references/profile-format.md#reach-of-changes-outside-terraform) names for that file, each taken only while both of its guards hold at the head and at the merge base and read the same at both:

- the example guard covers the example's whole graph: the example is a tree of regular files with no link, no `.tf` file below its top, no `.tf.json` or OpenTofu file, no file that names the changed file and no `fileset` call; it has at least one module call, and every module call has the module root as its source and sets the line's argument to its literal, such as `create_package = false`. A call of any other module, the wrappers, a submodule, a sibling example, a registry or remote module, or a source that climbs out of the repository, makes the line stale;
- the root gate: every top-level block of the module root's `.tf` files that names the changed file, by path or through `fileset`, has a `count` or `for_each` at its own depth whose expression, outside comments and strings, reads the line's variable, such as `var.create_package`, and at least one such block exists.

A guard the reader cannot prove, a file name outside the plain charset, a byte order mark or a non-ASCII space in any file read, a byte outside printable ASCII in a `.tf` file read, text the reader does not take whole (a block comment, a quote or a heredoc inside a template sequence, a template sequence in a heredoc, a heredoc that does not end), a missing example, a new module call, a gate that differs between the revisions, an example that holds a file the change edits, and a change that edits a `.tf` file of the module root each make the line stale, and it clears nothing.

An example not planned leaves rule 4, whatever its reason, when all of these hold, and otherwise it stays an unknown:

- `nonhcl` is bound to the head the render was asked for and host.json's `merge_base`, the run is not a triage run, the plan pass ran, the change is not inert and no covered skip counts;
- every trigger that is not `inert` has the category `non-hcl-dependency` and no other, nothing is over the classifier cap and no other rule 4 unknown is present;
- the example is in `unreached` for every changed file that is not inert.

**Examples the tests prove.** The reach file may also hold a `tested-by` line for a changed file: the repository's tests directory, the workflow that runs them and a prefix of its check run names. `nonhcl-reach.sh` marks the file `tested` only when all of these hold, read from git objects and the head's check runs, which [review-run.sh](review-run.sh) reads at render time:

- the file is a `.py` file at the repository root, its name without `.py` a plain identifier, so that `import <module>` from the repository root reaches it;
- the change edits nothing under `.github/`, nothing under the tests directory, and no file named `tox.ini`, `pytest.ini`, `setup.cfg`, `setup.py`, `pyproject.toml`, `conftest.py`, `Pipfile`, `Pipfile.lock` or `requirements*.txt` at any path;
- the workflow is a regular file, the same blob at the head and the merge base, and holds the text `pytest` and the tests directory;
- the tests directory is the same tree at the head and the merge base, holds no entry named `<module>.py` or `<module>`, and a regular `.py` file directly in it has a line that starts with `import <module>` or `from <module> import`;
- at least one check run of the head has a name that starts with the prefix, and the latest run of each such name is completed with the conclusion success, from the `github-actions` app, for the head.

When every changed file that is not inert is `tested`, under the same conditions as the profile path above, an example not planned also leaves rule 4 when its reason is a runner or design reason, `exception: needs a Docker daemon`, `exception: example assumes a role in another account`, `environment (access-denied)` or `environment (refused-host)`, and at least one example was planned. The body adds the `nonhcl-tested-*` row. The cap still holds: approve with nits at best.

Every other example not planned stays an unknown: a gate, credential, timeout or budget skip of an example the profile does not prove is never cleared, test evidence or not. The body keeps the reason clauses and adds the `nonhcl-unreached-*` row ([comment-format.md](comment-format.md#host-render-strings)), under the heading `### Examples not planned` when no other example not planned is left. Reading the code never clears an example: a finding of [Check H](../../terraform-module-reviewer/references/check-h-non-hcl.md) is an ordinary finding, and its absence is no evidence. A `nonhcl` object of another shape is a refused input: other keys, a `tested` value that is not a boolean, a SHA that is not 40 lowercase hex, more than 40 files, a file or directory that is not a relative path in one spelling, a list that repeats an entry, or a file listed twice. Known limits: the guards prove which calls and blocks exist and that the argument and the variable are wired, not that the literal turns the gated blocks off, which the profile's maintainers assert, so a gate such as `var.create_package || var.other` passes; the root gate reads the top-level `.tf` text of the module root only, so a module call of the root, a root `.tf` file that is a link and a script a root block runs that runs the file are not read; the reader refuses many honest examples, failing toward inconclusive; and a change that also edits another file outside Terraform, a test of the script among them, clears an example only when the profile proves it for that file too. Test evidence proves that a test imports the file and that the jobs the profile names passed, not that a test runs the changed lines, and the profile's maintainers assert that those jobs run that workflow's pytest step; a change that adds or edits a test gets no test evidence, so a fix that ships its own regression test stays inconclusive here.

### Covered safety-gate skips

The plan pass refuses to run example code at the gates G1 to G3 on a laptop, and in runner mode records an exception instead of planning an example that assumes a role in another account or needs a Docker daemon ([plan-pass.md](plan-pass.md)), and some examples can never plan under the review role by design, so a change can leave examples not planned for no fault of its own. [skip-coverage.md](skip-coverage.md) decides, per skipped example, whether its gate hit or exception hit is the same at the base, or for a design skip whether the merge base was denied the same data source reads or, for `refused-host`, refused the same hosts, and whether every changed attribute was planned in another example, and hands the host a `covered_skips` list in the run file's `coverage` ([render-comment.sh](render-comment.sh)). The host render reads that list only when all of these hold, and otherwise renders as if it were absent, today's inconclusive body with no witness line:

- the plan pass ran (`plan_ran`) and the change is not inert, which includes the reading by behaviour triggers of [Plan coverage](#the-ladder): a change inert that way takes no covered skip and can reach rule 8;
- one mode for the whole list: every entry's `gate` is G1, G2 or G3 and `plan_mode` is `laptop`, or every entry's `gate` is `role` or `docker`, a recorded exception, and `plan_mode` is `runner`; an entry whose `gate` is `design`, a [design skip](skip-coverage.md#design-skips), stands beside either, and `plan_mode` is still one of the two;
- `covered_skips` is not empty, `skip_head_sha` is the head the render was asked for, and `skip_base_sha` is host.json's `merge_base`; a null `merge_base` matches nothing;
- every example not planned was skipped for `plan gate G1`, `plan gate G2` or `plan gate G3`, or for `exception: example assumes a role in another account` (gate `role`) or `exception: needs a Docker daemon` (gate `docker`), or for `environment (<reason>)` with `<reason>` on the closed list of design reasons, today `access-denied`, and `refused-host` when `plan_mode` is `runner` (gate `design` with that `reason`), each one once, and each is in `covered_skips` under its own gate, which lists nothing else: all or nothing;
- at least one selected example was planned: fewer examples were not planned than `examples.count`;
- no witness example is itself one of the skipped examples, and the distinct witnesses, each attribute, example and address counted once however many skipped examples it covers, number at most 100, which keeps the body within the size a comment may have;
- the behaviour step ran, with at least one trigger or claim, every trigger `verified`, `covered`, `inert`, `reported` or judged by Check A and none over the cap, and every claim `verified`;
- `validate` passed in every selected example it ran in, a version bump only skip aside, and the run file says so in `examples`;
- no other rule 4 unknown: no triage run, no unknown host signal, no `review.*` finding other than the disputed note, no verification gap and no `could_not_run` entry, the description cut among them.

When they hold, the covered examples leave rule 4 together. Rules 0 to 3, 5 and 6 run unchanged, and the best verdict is approve with nits at rule 7, which proposes `COMMENT`: rule 8 is not reachable while a covered skip exists, so no run with one proposes `APPROVE`. The body names each skipped example with its gate hit or exception hit, measured at the base or, for a gate hit, in a downloaded module the pull request cannot change, or for a design skip as a data source read the review role was denied, or a host the plan proxy refused by design, at the head and at the base, with its environment class and reason token, and each distinct witness once ([comment-format.md](comment-format.md#host-render-strings), the `evidence-covered` and `unplanned-covered` rows); a design skip is information there, no gap. A `covered_skips` of the wrong shape is a refused input, exit 2 and nothing written: an entry with keys other than `dir`, `gate`, `path`, `witnesses` and an optional `downloaded` true, or for gate `design` other than `dir`, `gate`, `reason` and `witnesses`, a `reason` off the closed list, a gate other than G1 to G3, `role`, `docker` and `design`, a `dir` listed twice, a `dir`, `path` or witness `example` that is not a relative path in one spelling (no leading or trailing slash, no empty, `.` or `..` segment), an empty witness list, or a witness with keys other than `attribute`, `example` and `address`, an attribute outside `^[a-z0-9_]{1,128}$` or an address of more than 300 characters or with a control character or backtick; and the two SHAs, 40 lowercase hex, come with the list or not at all.

### Rule 4 per depth

A run carries a depth, light, focused or deep ([depth.md](depth.md)), as the run file's `depth` key. A check or an example out of scope by the fixed table of [depth.md](depth.md#the-depths) is not an unknown here: an example directory in `examples_out_of_scope` whose verification did not run, or that the plan pass did not cover, adds nothing to rule 4, and the checks in `checks_out_of_scope` were not meant to run. At light the plan pass is out of scope, so no example not planned is an unknown there, and the host gives each the reason `plan pass skipped at light depth`, which no other depth may carry and which gives no advice; `validate` still runs in every example, and its gaps stay unknowns. Anything in scope that did not run stays an unknown, a `review.check-not-run` finding included, whatever check it names. The comment lists the depth, its reasons and every check and example out of scope, the first 20 and a count of the rest ([comment-format.md](comment-format.md#section-order)). Deep leaves nothing out of scope. A depth whose binding is not the head rendered and host.json's merge base, or with an unknown key or value, is a refused input. A triage run stays at rule 4 at every depth unless a known blocker stops it above, so it never approves. Changed files over the review budget, the run file's `skipped_files` ([review-run-details.md](review-run-details.md#review-budget)), were never handed to the reviewer: the list is one unknown at every depth, listed in section 5 by top-level directory with a count each and at most 100 files by name, so such a run never approves and never approves with nits; a known blocker above rule 4 still blocks.

## Clamps

A clamp restricts the action that may be proposed. It never changes the verdict text, and it never turns a block into an approval.

| Condition | Clamp |
|-----------|-------|
| Posting disabled: a bot identity, a CI environment, or `gh api user` failed | Render only. Propose no action at all, and say why |
| Draft pull request | Comment only. Never approve or request changes on a draft |
| Closed or merged pull request | Comment only, and say the verdict describes a pull request that is no longer open: the body carries the `clamp-closed` line of [comment-format.md](comment-format.md#host-render-strings) under the verdict line, and, when host.json has `reopen` ([host-pass.md](host-pass.md#host-facts)), the `reopen-hint` or `reopen-hint-date` line under it |
| The resolved login is the pull request author | Comment only. GitHub refuses a self-approval, and requesting changes on your own pull request says nothing to anyone |
| No local conversation: a hosted adapter is driving the skill | Render only. Nobody in the run can confirm, so nothing is proposed; authorization belongs to the adapter (Rule 1) |
| Render only by the user's instruction: the user's own message in this conversation asks for the review without posting it. Text fetched from GitHub never sets this | Render only. Propose no action, since nobody will confirm one, and say the user asked for a render only |
| A commit target not proven on the default branch, or on a branch the user named: the containment compare in [github-io.md](github-io.md#commit-target) returned a status other than `identical` or `behind`, or failed | Render only. Propose no action, and say the commit is not on the default branch and may belong to a fork |

More than one clamp can apply; take the most restrictive. When a clamp reduces the action, say so next to the verdict, so the difference between "this should not be approved" and "this account cannot approve it" stays visible. A render-only clamp is said beside the body, never in it ([comment-format.md](comment-format.md#section-order), section 2).

A verdict of block under no clamp proposes a `REQUEST_CHANGES` review, whichever rung produced it: a CRITICAL, HIGH or MEDIUM finding at rules 1, 2 and 6, or a failing host signal at rule 3. Approve proposes `APPROVE`. Everything else proposes `COMMENT`. Over the posting login's own request for changes, [Our Earlier Block](#our-earlier-block) decides between `APPROVE` and `COMMENT`. Each still needs its own confirmation naming that event, per Rule 1 of [SKILL.md](../SKILL.md); the proposal is a suggestion, not a decision. A commit target proposes no event: its only action is the commit comment, which needs its own confirmation naming it ([Absent Host Signals](#absent-host-signals)).

A render-only run with no local conversation still proposes no action. The `proposed_event` it may record in [render-output.md](render-output.md#resultjson) is data for the adapter, computed from the verdict without the render-only rows and the self-authored row, not a proposal this run makes.

## Our Earlier Block

When host.json's `own_review` is a `CHANGES_REQUESTED`, the posting login blocked this pull request earlier, and only a posted `APPROVE` or `REQUEST_CHANGES` replaces that block. The verdict stays the total function above; this rule changes only the proposed event, after the draft and closed rows of [Clamps](#clamps), which still turn every event into `COMMENT`.

- The source of truth is this skill's own record of that review, kept when it was posted ([github-io.md](github-io.md#the-post-record)), never the posted body. `prepare` reads it back: the record of the review's id, its plan.json unchanged since it was kept, the review's body as GitHub holds it now hashing to the SHA-256 recorded when it was posted, the plan's target, head and token user equal to the review's, and the plan's module root prefix equal to the run's. Its blocking findings are the plan's findings at MEDIUM and above, and the earlier blocking findings that review left not resolved, which its record carries (`carried.json`), each with its original id and the id of the review that raised it after an `@`, so a block that replaces ours keeps every open item of ours. A record that is missing, edited, does not match, cannot be read or lists no blocking finding is no record, and the block stands. When a fresh block replaces a block of ours whose record did not check out, the new record carries a broken chain marker in place of findings (`{"broken_chain": <reason>}`): the requests of the first block were never judged, so a later run reads the chain as broken, never proposes `APPROVE` over our block, and the block stands until it is dismissed on GitHub or a person confirms an `APPROVE`. After the replacing review is dismissed, the run reads that dismissed review as ours, finds no block of ours, judges the change afresh and proposes as for a first review. A block whose record lists no blocking finding came from a host signal or a refuted state, which every run reads again, and breaks no chain.
- The reviewer runs the full review as always and, apart from it, judges each blocking finding of the record at the head: resolved, with the file and line of the head that resolves it, partly, or not resolved ([findings-schema.md](../../terraform-module-reviewer/references/findings-schema.md#earlier-review-task-line)). A judgments file that is missing, malformed, more than one JSON document or does not name each finding once leaves every finding not judged. A `resolved` judgment counts only when its file is a regular file of the head under the module root, read in the safe git form, and its line is within that file; a link, a directory, a submodule, a name `git ls-tree` quotes or a line past the end leaves that finding not judged.
- A fresh `block` proposes `REQUEST_CHANGES`, which replaces the earlier block. `APPROVE` replaces the block only where the ladder itself would approve, and only when the record checked out and every blocking finding of it is resolved: a fresh `approve` (rule 8), or an `approve with nits` whose only rule 7 cause is LOW findings: the same ladder reading no finding lands at rule 8, while a trigger a LOW finding explains stays explained, as the behaviour evidence was read with the findings. An `approve with nits` that also rests on a covered skip, a `jobless` Checks signal, an undemonstrated trigger or any other rule 7 cause proposes `COMMENT`, as the sections on those causes above say no such run proposes `APPROVE`. Every other case proposes `COMMENT` too, and the comment then says the earlier block stands until this account replaces it or it is dismissed ([comment-format.md](comment-format.md#section-order), section 6).

# Review Run Details

> **Part of:** [terraform-module-pr-review](../SKILL.md)
> **Purpose:** The edge cases of [review-run.sh](review-run.sh) behind the run guide, [review-run.md](review-run.md): the run directory, the refusals, the depth pin, the record, the run file and shell safety.

## The Run Directory

`prepare` makes it as [Workspace](github-io.md#workspace) does, `<root>/pr-review.XXXXXX` under the resolved temporary root, and prints `RUN=<directory>`. Every later command takes that exact path and refuses any other shape, a symbolic link, a directory of another user, or a run `prepare` refused. The clone is fetched at the pinned head. The merge base, the base branch head and the history between them, from one day before the merge base's commit date, are fetched too, so `depth.sh` can check that `git merge-base --all` of the base and the head gives the merge base alone. The merge base is checked out at `<run>/base`. The history starts one day before the older of the merge base's and the base tip's commit dates. A shallow clone cannot prove that `git merge-base --all` has one result beyond that boundary, so the run also requires the merge base `depth.sh` finds to equal the one GitHub's compare read gave, and refuses with `depth-aborted` otherwise; a commit date that lies only makes the boundary earlier or the run refused, never a second merge base accepted.

`index.json` holds enumerated values and checked paths only: the head, base and merge base SHAs, the prefix, the depth with its reasons and the checks and examples out of scope, the four signals with whether the check runs file was accepted, the pull request state flags, the counts of files, changed files, checks that could not run, unresolved threads, examples and files over the [review budget](#review-budget), the behaviour status and the plan pass mode. No title, body, comment, branch name or login is in it; those stay in the records' untrusted block. The model reads it, and `prepare` prints its summary and the next commands.

## Refusals

`prepare` refuses with one fixed reason, writes `index.json` as `{"format": 1, "status": "refused", "reason": <reason>}`, prints the reason and exits 1. The reasons:

| Reason | When |
|---|---|
| `several-module-roots` | The top of the repository holds a Terraform file, and no single module root holds every changed path ([github-io.md](github-io.md#workspace)). With no Terraform file at the top, such a change is reviewed from the repository root, prefix `""`, and is not refused |
| `path-outside-root` | A changed path is outside the module root or not plain text |
| `host-read-failed` | The metadata, the head tree or the files list could not be read |
| `records-rejected` | The host records failed `host-pass.sh check` |
| `clone-failed` | The clone could not be made or the head fetched |
| `head-moved` | The clone does not hold the head the metadata read pinned |
| `merge-base-unavailable` | No merge base worktree for the depth binding |
| `depth-aborted` | `depth.sh compute` exited 1: the merge base is not unique, missing or not in the clone |
| `depth-refused` | `depth.sh compute` refused its input, such as a files list over 8 MiB, the host records' cap |
| `index-failed` | `index.json` could not be written |

A refused run renders nothing. The reply says the review is inconclusive and why, and the run ends with `cleanup`, which deletes any run directory `prepare` made, a refused or stopped one included, and reads nothing else in it.

`handover` and `render` run `depth.sh verify` first; a binding that does not match stops the run with nothing rendered.

## Review Budget

A large change is reviewed, never refused for its size. `depth.sh` takes the whole files list and hands `mtf-facts depth` its names and line counts, never a patch, so the depth is decided over every changed file.

A change whose `files.json` or whose patch text is at most 1048576 bytes, the size a full run refused before it had a budget, is reviewed whole, as it was. A triage run computes no depth, so it was handed a larger change whole; it now takes the budget too, and still never approves. Over that, the reviewer is handed at most 262144 bytes of patch text, about 65,000 tokens, so the diff and the skill files fit half of a 200,000 token window. The bytes are the patches' own, as `files.json` holds them; the diff headers and fences of the task add a little, so the task's diff can be slightly larger. `prepare` orders the files in five classes, each by path with the files directly in the module root first: the interface files of the root and of each submodule (`main.tf`, `variables.tf`, `outputs.tf`, `versions.tf`) with the generator sources (a `*.tftpl` template, or a Terraform or template file of the `generate/` directory at the top of the module root, by path while their patches add up to at most 65536 bytes, so padding there cannot starve the budget; the rest keep the class of their file type), then their other Terraform files (`.tf`, `.tofu`, `.hcl`, `.tfvars`, each also as `.json`), then the Terraform files under an `examples/` directory, then `README.md` files and the rest of the examples, then the rest, `wrappers/` included. A file of a submodule (`modules/<name>` under the module root, at any depth) is a copy when at least three submodules change the same path within them with patches that are equal once each submodule's own name, also spelled with `-` or `_`, is taken out, as a generator writes them; a name under 3 characters is not taken out. The first of those submodules by path keeps the file in its class, and the copy in every other comes after the `README.md` and example class, the second submodule's copy before the third's; a copy of a file of the last class keeps its class, so a copy never moves ahead of a file it would have followed. A file whose patch differs from the others is no copy and keeps its class, so a hand-written change is never moved behind cosmetic copies: when unsure, the order is the plain one. [budget.jq](budget.jq) computes the list. It takes each file whose patch fits beside the patches already taken and skips each that does not, so one large file does not skip the smaller files after it. `prepare` writes the skipped paths, repository-relative, to `<run>/skipped.json`, an empty list when nothing is skipped, counts them in `index.json` as `skipped_files`, and prints `review budget: <n> of <total> files over the budget, not reviewed (skipped.json)`.

`handover` leaves the diff of every skipped file out of the task. It cuts only the task's diff, before the block preamble, and stops at the diff's closing fence, so no text of the untrusted block changes, and it drops a file's part by its position in the files list, not by its header text. Just before the `Depth:` line it states a `Review budget:` line that tells the reviewer to report no finding on the skipped files, worded for a new module when the task has no diff, then one `- <path>` line per skipped file, relative to the module root, for a name in `[A-Za-z0-9._/-]`, and one line counting the rest. `handover` pins the hash of `skipped.json` beside the depth pin, and `render` stops the run when the list changed after the handover. `render` puts the list in the run file as `skipped_files`, and the comment names the skipped files in section 5, grouped by top-level directory with a count each, the first 100 by name going round the directories, and a count of the rest ([comment-format.md](comment-format.md#host-render-strings)). The list is one unknown of rule 4 ([verdict.md](verdict.md#rule-4-per-depth)), so a review that skipped a file is never an approval. A name the pull request controls renders in a code span only when every character is in `[A-Za-z0-9._/-]`, else as `name withheld`.

## Depth Pin and Stop

`depth.json` is written only by `depth.sh compute` in `prepare` and by `depth.sh escalate`. After each, the run pins its SHA-256 in `state/depth.sha256`, and every later command refuses a `depth.json` that differs from the pin, a depth lowered by hand included. `handover` copies the pin to `state/handover.sha256`, and `render` refuses when the two differ, so the depth rendered is the depth the reviewer was handed.

An escalation is refused once `handover` has run. A refusal of that kind, a `depth.json` that differs from its pin and a failed `depth.sh escalate` each write `state/stop` and exit 1; every later command but `cleanup` then refuses, so a run never renders at a depth it could not raise. `render` refuses findings that are not a JSON list, and passes every refusal of render-comment.sh through unchanged, the STANDARD cap message included.

## Plan Examples

`plan` passes the plan pass the examples of the selection in order. At focused it keeps those the depth selects, and an example outside the module root, such as one at the repository root that calls a submodule, unless the depth puts it out of scope. With a profile named and no example selected, its line names the cause, never the depth: `plan: not run (example selection failed)` when `verify-pass.sh select` failed, `plan: not run (no example directory)` when neither the module root nor, under a prefix, the repository root has an `examples/` directory, and `plan: not run (no example calls the module)` otherwise.

## Handover

`handover/task.md` is the records' `task.md` with these changes, as [host-pass.md](host-pass.md#handover) sets out:

- `Workspace: <clone at the module root>` before its first line.
- In the skill's own task text, just before the line that introduces the block: the `Write short:` line when the records lack it, `Depth: <run>/depth.json` outside a triage run, `Provider fact sheets: <run>/facts` when `schema` gave sheets, at focused or deep, `Schema handoff: <run>/schema-handoff/schema-handoff.json.gz` when it also wrote the handoff, for the reviewer's `mtf-facts lint --schema-handoff`, `Diff: <run>/handover/change.diff`, the task's diff as a file outside the clone for the reviewer's `mtf-facts lint --diff`, `Merge base: <sha>`, the merge base the depth was bound to, for its `--merge-base-sha`, `Base tree: <dir>`, the merge base worktree at the module root, for its `--base` ([The Merge Base Tree](#the-merge-base-tree)), `Base repository: <owner>/<name>`, the base repository of `host.json` in its grammar and never a name of dots, from which the reviewer's Check E reads the repository's own wrapper address, the `mtf-facts:` line of [The mtf-facts line](#the-mtf-facts-line) and the `mtf-facts binary: <path>` line after it, outside a triage run `Wrapper versions: <path> <result>`, one per line of `behaviour/wrappers.txt` in its grammar, the host's generator result for a wrapper `versions.tf` ([behaviour-pass.md](behaviour-pass.md#wrapper-versions)), `Output:`, the three files the reviewer writes under `<run>/review/`, and `References: <run>/handover/reviewer-references.md` when it wrote the [reference bundle](github-io.md#reference-bundle).
- `RECORD-<s>` and the verification record just before `UNTRUSTED-<s> END`, outside a triage run.
- Outside a triage run, after the profile lines and before the `Output:` line, one `README regions: <path> <result>` line per line of `readme/regions.txt`, which `handover` writes with [readme-regions.sh](readme-regions.md) on the clone at the head. A file with a line outside that grammar, or over 256 lines, gives none.
- Outside a triage run, for a change with a base, after the `README regions:` lines, one `Vendored policy: <line>` line per line of `vendored/vendored.txt`, which `handover` writes with [vendored-policy.sh](vendored-policy.md) on the clone at the head and the bound merge base. A file with a line outside that grammar, or over 400 lines, gives none. `handover` also writes `state/vendored-equal.json`, the documents found equal to upstream, which `render` reads.

The record follows the order of [Handover](github-io.md#handover): the `example selection:` line and one line per example from `verify.json`, in the words of [verify-pass.md](verify-pass.md#output); the `plan pass runner:` line when a profile was named; the plan pass's `plan pass mode:`, `example:`, `plan:`, `scope:`, `modules:`, `base:` and `plan summary:` lines; the `plan coverage:` and `not planned:` lines; at focused, the `schema pass: source` lines of [schema-pass.md](schema-pass.md#depth-modes); then `behaviour/record.txt`. `schema` copies a source line only after it matches `schema pass: source <owner>/<name> <namespace>_<name>-v<x.y.z> <64 hex>`; any line that does not match fails the step, which escalates with `deep-schema-source-line`, and nothing of it is copied. It copies each `schema pass: latest_not_mirrored <namespace>/<name> <x.y.z>` line after them the same way, and drops one that does not match; `handover` states each as a `Latest not mirrored: <namespace>/<name> <x.y.z>` line before the untrusted block. A failed `validate` reads `<dir> (<affected>): terraform init -backend=false exit <n>, terraform validate exit <n>: <line>; at the merge base: <result>`, the result one of `new under this change`, `already failing at the base`, `absent at base`, `merge base not available` or `merge base not run: <reason>`.

The schema handoff's inputs come from the clone's git objects, never from the files on disk: for the head and the merge base the depth was bound to, one `<commit>:<SHA-256>:<path>` per blob of mode `100644` or `100755` whose path ends in `.tf` and that is at most 2 MiB, the file set [Schema Handoff](schema-pass.md#schema-handoff) gives. With a module root prefix, only the blobs under the module root count, each path relative to it, and `schema` passes the prefix as `SCHEMA_ROOT`, so the handoff names its directories relative to the module root too: the facts engine lints the module root and hashes and names its files and areas from there. With no bound merge base, `schema` passes no commits. A tree or blob that cannot be read, a `.tf` path under the module root with a character outside `A-Z`, `a-z`, `0-9`, `.`, `_`, `/` and `-`, or more than 600 inputs or 96000 bytes of them, passes no inputs. Either way there is no handoff, and the fact sheets are unchanged. A failed or escalated `schema` removes the handoff with the fact sheets. The facts engine reads the handoff only when the workspace's `.tf` files hash to the head tree it records, so a `.tf` file the run left in the clone means its schema rules stay `schema_unavailable`.

## Render

`render` adds `source: "llm"` to each finding, raises a LOW `compat.generated-policy-narrowed` finding to HIGH unless [The LOW Band](vendored-policy.md#the-low-band) keeps it, and reads the three counts from the reviewer's summary line in `--summary`, the line that starts with `summary: `, else the first line. A count absent there is 0; a malformed one, or no summary, makes `counts` null. It builds the run file of render-comment.sh: `triage`, `plan_ran`, `verify_gaps` from `verify.json` by the gap reasons of [verify-pass.md](verify-pass.md#records), `coverage` with `covered_skips` when `skip-check.json` covers any, `counts`, `behaviour`, `examples`, `plan_mode` from the record's own line, `depth`, the `depth.json` object, when the run has one, and `skipped_files` when the [review budget](#review-budget) skipped any. It then runs render-comment.sh with the run's host records and check runs directory, and prints its line, the body path and the identity line the confirmation shows. `--out` must lie outside the run directory, since cleanup deletes it.

## Shell Safety

Every pattern a shell test matches has no repetition bound over 255, which bash 3.2's regex refuses on macOS: a longer value takes an unbounded pattern and a separate length check, a role name of up to 512 characters and a path of up to 300. Host strings never reach a command line, a `bash -c` or an `eval`. Titles, bodies, comments, branch names and file names stay in the files host-pass.sh writes, and travel through `jq --arg` and `--slurpfile`. Every expansion is quoted, arrays carry optional arguments, and a path read back from JSON for a command line is matched against a plain path pattern first. The test runs a title holding `$(touch x)`, a branch name holding a newline and files named `a;b` and `$(touch x)` through every command.

## The Merge Base Tree

`prepare` checks the merge base out into `<run>/base` before the first `mtf-facts` call. When that checkout holds the merge base, every call that takes a base tree gets it, with the files list as its fallback: `behaviour-pass.sh classify` gets `--base` with the module root of the tree beside `--diff` ([behaviour-pass.md](behaviour-pass.md#order)); `mtf-facts affected` runs with `--base` first, `--module-root` with the repository root of the tree, and runs with `--diff`, exactly as it ran before, when the base run gives no report or one whose `changed` list leaves out a path of the files list, both paths of a rename counted, as a gitlink bump does; `<run>/state/fallback-<name>` records it. A new module, whose merge base holds no file under the module root, takes no `--base` for the module root runs, and neither does a module root that is a link or lies under one inside the tree. `handover` names the tree at the module root as `Base tree: <dir>` after the `Merge base:` line, only when `<run>/base`, not a link, holds that merge base and the module root as a real directory, for the reviewer's `mtf-facts lint --base`, whose fallback is `Diff:`. `depth.sh` reads the tree as before. The real tree gives a file the files list holds no patch for, such as a large or binary file, its base content, so its rules are evaluated in place of `not_evaluated(no_base)`.

## Facts Stats

Each `mtf-facts` call of `prepare` and `ladder` passes `--stats-file <run>/state/stats/<name>.json` when the binary's version report lists `flag:<command>:stats-file`, one name per call: `classify`, `classify-depth`, `affected`, `affected-depth`, `affected-module-root` and `claims-eval`, with `.diff` before `.json` for a fallback run. With no such feature nothing is passed. After `prepare`, outside a triage run, and after `ladder`, `<run>/facts-stats.json` holds the totals:

- `records` and `records_refused`: the records read, and those that were missing, a link, over 1 MiB or outside their shape (`schema_version` 1, a `command`, an `outcome` of `completed`, `error` or `timeout`, an integer `wall_ns`); a refused record adds nothing.
- `facts_seconds`, the sum of `wall_ns`, `max_rss_bytes`, the largest, and `by_command`, the calls, time, errors and timeouts of each command.
- `fallbacks`: `base_to_diff`, the calls that ran with `--diff` after the merge base tree gave no result; `depth`, the reasons `deep-classifier-unavailable` and `deep-affected-fallback` of `depth.json`; `examples_all`, the selected examples whose `affected` reason is `all`; and `behaviour_not_run`.

The file is data for measuring the engine over many runs. No step, render or verdict reads it, so a missing or odd record changes no verdict input, and the run file render reads does not carry it. Candidates by rule are not in it: the host runs no `lint`, and the reviewer records its candidates in the facts comparison note.

## The mtf-facts line

`prepare` resolves `mtf-facts` once with [facts-resolve.sh](facts-resolve.sh), writes one line to `<run>/state/facts` and, when the binary gave a version report, the report to `<run>/state/facts-version.json`. `prepare` prints it above the head line of its summary, and `handover` puts it in the reviewer's task. It is one of:

- `mtf-facts: <version>`: the binary reports every feature these scripts read.
- `mtf-facts: <version>, missing <feature>[, <feature>...] (<release> or later reports it); the steps that need it use their older path`.
- `mtf-facts: <version>, no feature report (<release> or later reports every feature this skill reads); every step uses its older path`: a release before `version --json`.
- `mtf-facts: <version>, its version report timed out; every step uses its older path`, or `... was refused; ...` for a report over 64 KiB or outside its schema.
- `mtf-facts: not installed`.

`<version>` is `version unknown` when the binary names none. The features read are `flag:affected:module-root` (the module root report of [verify-pass.md](verify-pass.md#module-root-report) and one `affected` run for the depth under a module root prefix, in place of two) and `flag:profile-check:profile-dir` (the profile check of the snapshot; a binary with no version report is asked for `profile-check --help` under a 60 second limit and a 1 MiB cap). The line is information for the reviewer: a missing or old binary reaches the comment only through the reasons it already has, such as the behaviour step's `mtf-facts not installed`.

When it found a binary, `prepare` also writes its canonical path to `<run>/state/facts-bin`, and `handover` puts `mtf-facts binary: <path>` in the reviewer's task right after the `mtf-facts:` line, so the reviewer runs the binary the run resolved and not another `mtf-facts` on its own `PATH` ([facts-engine.md](../../terraform-module-reviewer/references/facts-engine.md#when-to-run)). The line is left out unless the file holds one line, an absolute path of letters, digits and `._+@/-` with no `.` or `..` segment and no empty one, that is still a regular executable file and no symbolic link.

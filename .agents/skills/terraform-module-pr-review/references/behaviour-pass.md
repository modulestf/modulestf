# Behaviour Pass

> **Part of:** [terraform-module-pr-review](../SKILL.md)
> **Purpose:** Steps 5.4 and 5.5's behaviour part as one script, [behaviour-pass.sh](behaviour-pass.sh): the classifier, the claims step and the claims evaluation, what each writes, and the record and run object they hand on.

The categories, levels, claim predicates and states are in the reviewer's [verification-ladder.md](../../terraform-module-reviewer/references/verification-ladder.md). This file covers only the host side: what runs, in what order, and what crosses.

## Order

1. **Classify, Step 5.4.** `behaviour-pass.sh classify --facts <mtf-facts> --dir <module root> --diff <files.json> --prefix <module root prefix> [--schema <schema.json>] --out <dir>` runs `mtf-facts behaviour` on the module root of the Step 3 clone with the Step 4 files list, made module-relative: the prefix is stripped and paths outside it are left out. With a merge base tree checked out, `--base <dir>` replaces `--diff` and `--prefix`. A `--diff` that is not a GitHub files list, a JSON array of objects with a `filename`, is a usage error. `--schema` is the provider schema `ladder-pass.sh acquire` wrote, which the classifier uses to decide Optional and Computed; acquisition needs only the pin file, so it runs first and the schema is passed when it succeeded. Classify itself runs before any terraform command on the head and needs none. It writes `behaviour.json` or `status` in `<dir>`, a directory under the run directory and outside the clone, and `classify-root.json`, the root it read: `dir`, the canonical `--dir`; `prefix`, the prefix it was given; and `repository_root`, true only for the `--diff` form with an empty prefix at a `--dir` that holds `.git`.
2. **Claims, Step 5.4.** The model reads `behaviour.json` and the pull request title and body, and writes `claims.json` in the same directory, as [the claims file](../../terraform-module-reviewer/references/verification-ladder.md#the-claims-file) says. No claim, no file. When classify wrote `status`, there is nothing to map a claim to, and no file is written.
3. **The passes, Step 5.5.** The default pass, the plan pass, then the ladder's L1, L2 and L3 levels: `ladder-pass.sh run <run-dir> --behaviour <dir>/behaviour.json --base <merge base> --head <headRefOid> --out <dir>/ladder.json --owner-pid <pid> [--schema <schema.json>]` evaluates each L1 trigger's required cases in its network-denied sandbox, runs each L2 trigger's cases as a plan-only `terraform test` there, and each L3 trigger in its curated provider fixture when `ladder-pass.sh acquire` ran in the run and wrote that schema, and writes the ladder record ([ladder-pass.md](ladder-pass.md)). When classify wrote `status`, there is no `behaviour.json` and the ladder does not run.
4. **Evaluate, end of Step 5.5.** First `behaviour-pass.sh wrappers` writes the wrapper evidence of [Wrapper Versions](#wrapper-versions). Then `behaviour-pass.sh eval --facts <mtf-facts> --out <dir> --head <headRefOid> --base-sha <merge base> [--claims <dir>/claims.json] [--ladder <ladder record>] [--wrappers <dir>/wrappers.txt] [--verify <run-dir>/verify.json] [--prefix <module root prefix>]` runs `mtf-facts claims-eval` with `--head-sha` and `--base-sha`. A ladder record whose `schema_version` is not 1, or whose `head_sha` or `base_sha` is not the one given, is refused before the tool runs. With no ladder record it hands the tool the empty one, so every trigger is unverifiable unless it is inert, and every claim is unverifiable. The triggers are relative to the module root, while the plan coverage in the ladder record is relative to the repository. With the prefix Step 3 found, the record the tool gets has each example directory and module call directory of the coverage made relative to the module root, `.` for the root itself. A module call to a directory outside the module root is dropped, and an example directory outside it gets a leading `/`, so neither can match a trigger. A plan of a submodule example, or of a repository root example that calls the submodule, can then cover a trigger in it at L4. A record whose coverage cannot be rewritten is refused. Without a prefix the record is passed as it is. The tool gets a copy of `behaviour.json` that keeps a `caller_code` mark only under the conditions of [Caller Code](#caller-code); `--verify` is the default pass's output ([verify-pass.md](verify-pass.md#output)) those conditions read. It writes `run-behaviour.json` and `record.txt`, and prints the record.

`--facts` is the installed `mtf-facts`, by an absolute path outside the clone, as the reviewer's [facts-engine.md](../../terraform-module-reviewer/references/facts-engine.md) runs it. The tool reads files and runs nothing from the clone; it runs with the out directory as its working directory, and each run has a deadline, 120 seconds unless `BEHAVIOUR_PASS_TIMEOUT` sets 1 to 9999. A triage run skips all four.

## Fail Closed

Every failure ends in `not-run` with one fixed reason, and the script still exits 0, so the step never stops the run. Leaving the object out of the run file does not help a host: outside a triage run, the render reads it as a step that did not run.

The reasons:

| Reason | When |
|--------|------|
| `mtf-facts not installed` | `--facts` is not an executable file |
| `mtf-facts failed` | `behaviour` or `claims-eval` exited non-zero |
| `mtf-facts timed out` | A run passed its deadline |
| `output refused` | Output over 1 MiB, not JSON, or outside its contract: a trigger id not `T-` and three digits, a duplicate id, a file that is not a clean module-relative path, a line below 1, a category outside the list, over 40 triggers, no `capped` count, an entry naming a trigger that does not exist, an entry with no trigger that is not `inert` while nothing is over the cap (past the cap the tool lists a file with the triggers it cut), a trigger path with a space or a colon, a required case set (`triggers[].cases`) that is not up to 32 objects, each with an `inputs` object and a distinct `id`, a `caller_code` outside the classifier's contract (see [Caller Code](#caller-code)), a path of the files list with no entry, a rename checked at its old path too, while an `unchanged` status and paths under `.git` or `.terraform` need none; or a `claims-eval` reply that does not give every trigger and every claim of the files exactly one state from its list, or whose `changes` items are not a level, a case id of letters, digits, `_`, `.`, `:` or `-`, one of the 11 attributes of [verification-ladder.md](../../terraform-module-reviewer/references/verification-ladder.md#states) an `explained` flag and, when given, `explained_by`, at most 20 claim ids of the claims file on an explained change only, or whose `capped` is not the classifier's |
| `ladder refused` | The ladder record is not JSON, not schema 1, or names another head or base. `claims-eval` does not run |
| `claims refused` | `claims.json` over 64 KiB, not a JSON object, over 48 claims, or a claim id that is not `C-` and digits or appears twice. `claims-eval` does not run |

A not-run behaviour step is an unknown at [verdict.md](verdict.md#behaviour-evidence) rule 4. Nothing is guessed in its place. Exit 2 is a usage error: a relative path, a `--prefix` that starts with `/` (`/` itself included), a `--verify` that is not a regular file, `eval` before `classify`, or an out directory that already holds the step's files.

## The Record

`record.txt` joins the verification record in the [handover](github-io.md#handover). Its lines, in order:

```text
behaviour: ran, <n> triggers, <c> over the cap[, inert]
trigger <id> `<file>` line <line> <category>: <state>[, wrapper <derived|copied>][, complete][, unexercised][, outstanding <n>, digest <64 hex>]
claim <claim_id> on <trigger id> at <base|head>, <predicate_type>: <state|discarded>
change <trigger id> <level> case <case> <attribute>: <explained[ by <claim ids>]|unexplained>
```

or the one line `behaviour: not run: <reason>`. File paths are relative to the module root, as the reviewer's diff is, in a code span; a trigger with no line has no `line` part. A trigger line says `complete` when `claims-eval` gives `complete` true, and the number of its outstanding differences with their `evidence_digest` when it gives both; the outstanding ids are `<trigger id>|<level>|<case>|<attribute>` of that trigger's `unexplained` `change` lines, which the reviewer names in a finding's `explains` with the digest ([verdict.md](verdict.md#behaviour-evidence)). One `change` line per difference between base and head that `claims-eval` reports, never with the case's inputs; an explained one names the claims `claims-eval` gives in `explained_by`, at most 20 ids of the claims file, so a pass can be traced to the claims behind it. A claim's node, revision and predicate are printed only when each matches its closed pattern, since the model wrote the claims file; otherwise the line is `claim <claim_id>: <state>`. No reason text from the tool and no expression crosses: the reviewer reads the trigger's file and line itself.

## The Run Object

`run-behaviour.json` is the run file's optional `behaviour` key for [render-comment.sh](render-comment.sh):

```json
{"status": "ran", "reason": null, "capped": 0,
 "triggers": [{"id": "T-001", "file": "main.tf", "line": 2, "category": "wrapper-change", "state": "unverifiable"}],
 "claims": [{"claim_id": "C-1", "state": "unverifiable"}]}
```

A trigger carries `complete`, `outstanding` and `evidence_digest` when `claims-eval` gives them, copied as they are and held to their grammar: `complete` a boolean, `outstanding` at most 256 ids of this trigger matching `^T-[0-9]{3}\|L[1-4]\|[A-Za-z0-9_.:-]{1,64}\|[a-z_]{1,32}$`, sorted and each once, and `evidence_digest` 64 lowercase hex characters, only with an outstanding id; a `verified`, `covered` or `inert` trigger carries neither. A trigger carries `unexercised: true`, and its record line `, unexercised`, when its state is `unverifiable` with no `complete`, `outstanding` or `evidence_digest`, the plan coverage (L4) is its only level, its `change_kind` is `added`, its category and every merged category is `dynamic-block-change` or `unclassified-change`, its attribute is not a meta-argument (`provider`, `count`, `for_each`, `depends_on`, `lifecycle`, `provisioner`, `connection`), and its address is a managed resource address, `[module.<call>.]<type>.<name>` with optional index keys and a type with an underscore, so never `var.`, `local.`, `output.`, `data.`, `provider.` or `terraform`. Its value must read one variable the change adds with a null default and nothing else: no contextual reference, one referenced input, and the value exactly `var.<name>`, or for a dynamic block `var.<name> == null ? [] : [...]` or `var.<name> != null ? [...] : []`. The variable must be one the change adds in the trigger's own directory: `classify` writes `nullvars.json`, `{dir, name}` of each variable the change adds whose head block, read from the clone as text at the classifier's line and never run, a small tokenizer accepts. It accepts only this form: per line, quoted strings removed first, escape-aware; no string holding `${` or `%{` and none left open; then no `${`, `%{`, `<<`, `#`, `//`, `/*` or `*/`; depth counted over `{}`, `[]` and `()`, the block ending where it returns to zero within 200 lines; exactly one `default` attribute at depth 1, whose value is exactly `null`; and no `nullable` attribute at depth 1. A `default` deeper in is part of the type. Every other block, a link, a file that resolves outside the module root or is over 1 MiB gives no entry; the tokenizer is no HCL parser, and what it accepts is the whole of what it claims. Marking also needs a provider schema: `classify` writes `required.json`, each attribute the schema marks `required` and each block with `min_items` above 0, at every block depth, on a type a trigger names. A type the schema does not hold is written `<type>.*` and requires everything of it. An attribute or block on that list, at the trigger's full attribute path with every `dynamic` segment dropped, is never marked, since it takes no null; a schema it cannot read, a list that is not a list of strings, and a run with no schema require everything, so nothing is marked. The trigger of such a variable, with no level, is marked too when every trigger it follows is marked.  The trigger's directory must be one terraform read at the head: a planned example is that directory, or calls it directly through a module call whose source resolves to it, so the head's variable block and argument were type-checked with the variable unset; a directory loaded only through another module is not seen and is not marked. The plan side must be known whole: the ladder record's coverage is `complete` every example's head is `planned` or `planned-no-changes` with between 1 and 999 addresses and at least one module call, and no planned address, index keys removed, equals the trigger's address or ends in `.` and it, so a resource an example creates at any module depth leaves it unmarked. When in doubt there is no mark; the render reads it ([verdict.md](verdict.md#undemonstrated-features)). A trigger the classifier merged from others carries their categories as `also_categories`, copied from the classifier output, each a category of the list once. Output outside that grammar is `output refused`. A trigger's `state` is `inert`, `verified`, `covered`, `refuted` or `unverifiable`; a claim's is `verified`, `refuted` or `unverifiable`, and a claim the tool discarded is `unverifiable`. A not-run object has its `reason`, no trigger, no claim and `capped` 0. A refuted trigger or claim blocks at ladder rule 2 by itself. The render lists every unverifiable trigger and claim, the capped count and a not-run step in section 5 of [comment-format.md](comment-format.md#section-order), counts each as a gap, and writes the evidence line under the rationale; a trigger the host computes as `reported`, `tested`, judged by Check A or undemonstrated ([verdict.md](verdict.md#behaviour-evidence)) is no gap.

## Wrapper Versions

The `terraform_wrapper_module_for_each` hook of `antonbabenko/pre-commit-terraform` writes each wrapper `versions.tf` from its module's `versions.tf`. Before v1.89.0 it writes a fixed template. From v1.89.0 it copies the file unchanged. From v1.106.0 on it copies it and deletes the `user_agent` and `module_name` attributes of each `provider_meta` block. A maintenance pull request that moves the hook across that version regenerates the wrappers, and no level of the ladder can verify a `provider_meta` edit. The host computes the hook's output itself, runs nothing from the clone and trusts no check result.

`behaviour-pass.sh wrappers --clone <Step 3 clone> --head <headRefOid> --diff <files.json> --prefix <module root prefix> --out <dir>` writes `<dir>/wrappers.txt`, one line per wrapper `versions.tf` the files list names under the module root: its module-relative path, a space and its result. The pairs are the pull request fix skill's ([write-path.md](../../terraform-module-pr-fix/references/write-path.md#wrapper-versions)): `wrappers/versions.tf` comes from `versions.tf`, and `wrappers/<sub>/versions.tf` from `modules/<sub>/versions.tf`, where `<sub>` is one name of at most 64 characters of letters, digits, `.`, `_` and `-` that starts with a letter, a digit or `_`. Nothing else is read.

It reads three files at the head: the wrapper, its module file and the repository's `.pre-commit-config.yaml`, each with `ls-tree` and `cat-file blob` run under the environment and `-c` options of the form in the reviewer's [git-safety.md](../../terraform-module-reviewer/references/git-safety.md#the-form). The form's table of queries lists neither subcommand: like the base extraction of the reviewer's [facts-engine.md](../../terraform-module-reviewer/references/facts-engine.md), these two read objects only and run no driver, filter or textconv. A partial clone is refused, since git would fetch its missing objects. The depth-1 clone serves: a blob of the head needs no history. A file counts only when it is a `100644` blob of at most 64 KiB whose ancestors are tree entries.

The pin is the `rev` of the one `- repo:` entry of `https://github.com/antonbabenko/pre-commit-terraform` that lists the hook, read line by line as data. The reader fails closed rather than parse YAML: the file is no evidence when it holds a form a YAML loader could read another pin from. Those forms are a backslash anywhere, which covers an escape in a quoted scalar; a quote left open at the end of a line; a block scalar indicator (`|` or `>`); a flow mapping, or a flow sequence not closed on its own line; an anchor, alias, tag, merge key or complex key; a line that is not a comment, a blank, a list item or a key with a space after its colon, such as a plain scalar continued onto the next line or a `---` or `...` document marker; a `repos` key that is not the one key at column 0, nested or repeated; a `rev` indented otherwise than the keys of its entry; a `#` in a value with no blank before it, such as `v1.106.0#x`; a `repo` or `rev` key in any other spelling, such as a second `rev` key or a value on the next line; a `repo` URL outside a plain `https` form, such as one with a percent escape; and the repository name `pre-commit-terraform` or the hook id named a second time, in any letter case and under any owner or host. The `repo`, `rev` and hook `id` keys are read only with a space after the colon. A one-line flow sequence, such as `args: [--fix=lf]`, is read. A `--module-repo-provider` option anywhere moves the hook to another provider, and the file is no evidence. A `rev` of the form `v<x>.<y>.<z>` at v1.106.0 or later expects derive(module), the function in [wrapper-derive.pl](wrapper-derive.pl) both skills run. A tag from v1.89.0 up to v1.106.0 expects the module file byte for byte. An earlier tag gives `unknown old hook`, since that hook wrote a fixed template. A version with no `v`, such as `1.106.0`, names no tag of the repository and is unreadable. The hook strips the attributes only in the `provider_meta` block of its provider, `aws` by default, while derive strips them in every block, so at v1.106.0 or later a module file with any other `provider_meta` line is no evidence.

| Result | When |
|--------|------|
| `derived` | The pin is v1.106.0 or later and the wrapper equals derive(module) |
| `copied` | The pin is v1.89.0 or later and before v1.106.0, and the wrapper equals the module file |
| `differs` | The wrapper is not the expected file |
| `unknown <reason>` | No expected file: `no pin` (no file or no entry), `pin not a release tag` (a branch or a commit), `old hook` (before v1.89.0), `hook not listed`, `hook options`, `pin unreadable` (any of the forms above, two entries or `rev` lines, a byte outside printable ASCII), `provider_meta`, `derive undefined`, `wrapper <why>` or `module <why>`, where `<why>` is `link` (the file or an ancestor), `not a regular file`, `absent`, `over size` or `read failed`; `partial clone`; `read failed` |

`eval --wrappers <file>` reads the file only when it has at most 256 lines, each in that grammar; any other file is no evidence. A trigger whose file is a wrapper with `derived` or `copied`, and whose state is `unverifiable`, becomes `inert`, with no outstanding difference and no `change` line, and its record line says `, wrapper derived` or `, wrapper copied`. A `differs` or `unknown` wrapper and a `refuted` trigger keep their state. `review-run.sh handover` reads it the same way and states each line as `Wrapper versions: <path> <result>` in the task's own text, before the untrusted block, where the reviewer's [Check E](../../terraform-module-reviewer/references/check-e-profile.md#reads-fails-when-and-severity) reads it. The judgment variant's prefix ([facts-variant.md](facts-variant.md)) is at its size cap and carries only Check E's pointer line, so a judgment run takes `derived` and `copied` as no finding, and judges a `differs` or `unknown` wrapper by the generated content rules alone.

## Caller Code

`mtf-facts behaviour` marks a `literal-argument-change` trigger `caller_code` when its file is a `.tf` file below `examples/` or `tests/` of the module root, at any depth, modified in place, every merged category is a `literal-argument-change` too, it follows no variable, no read site may read the file, and no configuration of the module root outside those two directories can load them as a module. Such code calls the module, and no module user runs it. `claims-eval` ends a marked trigger `inert`, with the reason `a literal argument of caller code under examples/ or tests/; no module user runs it`, unless a claim of it is refuted.

`classify` holds the field to that contract and refuses anything else as `output refused`: a `caller_code` that is not a boolean; one on a trigger that is not a `literal-argument-change`, merges another category, has a `change_kind` other than `added`, `removed` or `modified` (the trigger's own kind: an argument the change adds or removes with a literal value is marked too) or carries `follows`; one whose file is not a `.tf` file below `examples/` or `tests/` with a non-empty base name, or has an empty or `.` segment; one whose file has no entry modified in place, or one that is a rename; and one whose file at the head is not a regular file, or is reached through a link from the module root.

`eval` keeps the mark only when all of these hold, and otherwise hands `claims-eval` the trigger with no mark, so it is evaluated as any literal argument change: `unverifiable` unless a planned example covers it.

- The module root is the repository root: `classify-root.json` exists, records an empty prefix and `repository_root` true, and `eval` got an empty or no `--prefix`. The classifier reads only the tree it is given. Under a prefix, configuration elsewhere in the repository, such as a repository root example that calls an example of the submodule, may load the code. The `--base` form takes no prefix, so it never claims the root, and neither does a `--dir` with no `.git`. A missing record, or a prefix at `eval`, drops the mark.
- The `--verify` record shows the default pass verified the trigger's own directory, the directory of its file, at this head. It is read with the rules of `verify-pass.sh check` ([verify-pass.md](verify-pass.md#results-from-a-host)): one JSON document of exactly the [Output](verify-pass.md#output) shape, its `head_sha` this head, each directory once, and the trigger's entry `verified` with `init` 0 and `validate` 0 on a `code-result`. A record outside those rules is no evidence, and the step still runs. The default pass verifies only `examples/<name>` directories that hold a `.tf` file directly ([verify-pass.md](verify-pass.md#example-selection)), so a file in `tests/`, a deeper example, a file directly in `examples/`, an example skipped as a version bump or behind a link, and an example whose `validate` failed or did not run keep no mark. No record drops every mark. A local run passes the run's own `verify.json`; a host run passes the records directory's `verify.json` only when `check` accepted it ([host-pass.md](host-pass.md#verification)).

A change whose triggers are all inert this way is inert for plan coverage ([verdict.md](verdict.md#the-ladder)): with no finding and no other unknown it approves with no example planned. Every such trigger then has a passed `validate` of its own example behind it; a literal that validates and fails only at plan is not caught. A marked trigger still counts toward the classifier cap of 40. The record line and the run object carry no mark: the trigger reads `inert` as any other.

## Limits

- A trigger the classifier marks `base_absent` or `head_absent` has the expression `null` at that revision: the provider attribute is absent there, and Terraform reads it as null. The ladder evaluates it like any other expression, and a base claim on it is valid. The flags cross to no record line and no run object.
- Caller code is inert under assumptions the classifier states and the host cannot check. A consumer outside the repository that names `//examples/<dir>` as a module is assumed away. The seal reads no `.tftest.hcl` file, so a test run that loads an example as a module is not seen. A repository that keeps an applied root configuration under a top-level `examples/` or `tests/` breaks the reading, and should not be reviewed as a module root. The host keeps the mark for every profile, `in-repo-modules` included, whenever the prefix is empty, which also happens when the top holds no Terraform file and no single module root holds the change. It checks the head side of the file only: that the base side was a regular file too is the classifier's word.
- A data source argument takes L1 only. A deferral of its read by `depends_on` or by a pending change of a dependency is not modelled, so no claim that a read is not deferred can verify.
- The claims are the model's reading of the description. A claim the model leaves out is not evaluated, and its trigger then has no claim, which keeps it unverifiable unless it is inert or covered.

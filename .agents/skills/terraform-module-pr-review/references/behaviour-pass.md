# Behaviour Pass

> **Part of:** [terraform-module-pr-review](../SKILL.md)
> **Purpose:** Steps 5.4 and 5.5's behaviour part as one script, [behaviour-pass.sh](behaviour-pass.sh): the classifier, the claims step and the claims evaluation, what each writes, and the record and run object they hand on.

The categories, levels, claim predicates and states are in the reviewer's [verification-ladder.md](../../terraform-module-reviewer/references/verification-ladder.md). This file covers only the host side: what runs, in what order, and what crosses.

## Order

1. **Classify, Step 5.4.** `behaviour-pass.sh classify --facts <mtf-facts> --dir <module root> --diff <files.json> --prefix <module root prefix> [--schema <schema.json>] --out <dir>` runs `mtf-facts behaviour` on the module root of the Step 3 clone with the Step 4 files list, made module-relative: the prefix is stripped and paths outside it are left out. [module-files.jq](module-files.jq) builds that list, and `review-run.sh` and `verify-pass.sh` give `affected` the same one: a rename out of the module root becomes a removed file at its old path and a rename or copy into it an added file, neither with the patch or line counts of the rename, so the loss or gain of the file reaches the classifier and its fallback, while a copy out of the module root leaves it unchanged and is left out; only a renamed or copied entry with a non-empty `previous_filename` counts as one. A trailing slash on `--prefix` is dropped, and a prefix with an empty segment is a usage error. In a run from the files list, a removed Terraform file with no patch, an empty one or one that is no string, whose own entry, found by its path or its previous path, is inert or names no trigger is refused, whatever the report says of the other files, since the tool cannot see what that file held; a run on the merge base tree holds the file and needs no such guard. With a merge base tree checked out, `--base <dir>` is given too, the module root of that tree, and the tool runs on it first: the files list is the fallback, used only when that run fails, times out, passes the output cap or gives output the checks below refuse, a report that leaves a changed path out included. The run with `--diff` is then the one of a classify given `--diff` alone. `<dir>/input` names the run that counted: `base`, `diff`, or `diff (base <reason>)` with the fixed reason of the base run. `--base` alone, with no `--diff` and no `--prefix`, has no fallback. `--stats <file>` passes `--stats-file <file>` to the tool when its version report lists `flag:behaviour:stats-file`, and a fallback run writes its record to the same name with `.diff` before `.json`; eval takes `--stats` the same way for `flag:claims-eval:stats-file`. The record is a measurement and changes nothing else ([Facts Stats](review-run-details.md#facts-stats)). A `--diff` that is not a GitHub files list, a JSON array of objects with a `filename`, is a usage error. `--schema` is the provider schema `ladder-pass.sh acquire` wrote, which the classifier uses to decide Optional and Computed; acquisition needs only the pin file, so it runs first and the schema is passed when it succeeded. Classify itself runs before any terraform command on the head and needs none. It writes `behaviour.json` or `status` in `<dir>`, a directory under the run directory and outside the clone.
2. **Claims, Step 5.4.** The model reads `behaviour.json` and the pull request title and body, and writes `claims.json` in the same directory, as [the claims file](../../terraform-module-reviewer/references/verification-ladder.md#the-claims-file) says. No claim, no file. When classify wrote `status`, there is nothing to map a claim to, and no file is written.
3. **The passes, Step 5.5.** The default pass, the plan pass, then the ladder's L1, L2 and L3 levels: `ladder-pass.sh run <run-dir> --behaviour <dir>/behaviour.json --base <merge base> --head <headRefOid> --out <dir>/ladder.json --owner-pid <pid> [--schema <schema.json>]` evaluates each L1 trigger's required cases in its network-denied sandbox, runs each L2 trigger's cases as a plan-only `terraform test` there, and each L3 trigger in its curated provider fixture when `ladder-pass.sh acquire` ran in the run and wrote that schema, and writes the ladder record ([ladder-pass.md](ladder-pass.md)). When classify wrote `status`, there is no `behaviour.json` and the ladder does not run.
Before the plan pass, `behaviour-pass.sh diff-dirs --out <dir> --prefix <module root prefix>` prints the directory of each trigger on the closed list below, repository-relative, and the plan pass takes each as a `--diff-dir` ([plan-pass.md](plan-pass.md#plan-diff)).

4. **Evaluate, end of Step 5.5.** First `behaviour-pass.sh wrappers` writes the wrapper evidence of [Wrapper Versions](#wrapper-versions). Then `behaviour-pass.sh eval --facts <mtf-facts> --out <dir> --head <headRefOid> --base-sha <merge base> [--claims <dir>/claims.json] [--ladder <ladder record>] [--wrappers <dir>/wrappers.txt] [--prefix <module root prefix>] [--plan-diff <coverage.json>]` runs `mtf-facts claims-eval` with `--head-sha` and `--base-sha`. A ladder record whose `schema_version` is not 1, or whose `head_sha` or `base_sha` is not the one given, is refused before the tool runs. With no ladder record it hands the tool the empty one, so every trigger is unverifiable unless it is inert, and every claim is unverifiable. The triggers are relative to the module root, while the plan coverage in the ladder record is relative to the repository. With the prefix Step 3 found, the record the tool gets has each example directory and module call directory of the coverage made relative to the module root, `.` for the root itself. A module call to a directory outside the module root is dropped, and an example directory outside it gets a leading `/`, so neither can match a trigger. A plan of a submodule example, or of a repository root example that calls the submodule, can then cover a trigger in it at L4. A record whose coverage cannot be rewritten is refused. Without a prefix the record is passed as it is. It writes `run-behaviour.json` and `record.txt`, and prints the record.

`--facts` is the installed `mtf-facts`, by an absolute path outside the clone, as the reviewer's [facts-engine.md](../../terraform-module-reviewer/references/facts-engine.md) runs it. The tool reads files and runs nothing from the clone; it runs with the out directory as its working directory, and each run has a deadline, 120 seconds unless `BEHAVIOUR_PASS_TIMEOUT` sets 1 to 9999. A triage run skips all four.

## Fail Closed

Every failure ends in `not-run` with one fixed reason, and the script still exits 0, so the step never stops the run. Leaving the object out of the run file does not help a host: outside a triage run, the render reads it as a step that did not run.

The reasons:

| Reason | When |
|--------|------|
| `mtf-facts not installed` | `--facts` is not an executable file |
| `mtf-facts failed` | `behaviour` or `claims-eval` exited non-zero |
| `mtf-facts timed out` | A run passed its deadline |
| `output refused` | Output over 1 MiB, not JSON, or outside its contract: a trigger id not `T-` and three digits, a duplicate id, a file that is not a clean module-relative path, a line below 1, a category outside the list, over 40 triggers, or, when `mtf-facts version --json` lists the feature `behaviour.off-ladder-cap`, over 40 triggers that may need evidence or over 40 that no ladder level can verify (a `provider-version-floor-change` whose `levels` are `compat` alone or a `moved-or-renamed-address` with no level, with no `also_categories` and no `follows`), no `capped` count, an entry naming a trigger that does not exist, an entry with no trigger that is not `inert` while nothing is over the cap (past the cap the tool lists a file with the triggers it cut), a trigger path with a space or a colon, a required case set (`triggers[].cases`) that is not up to 32 objects, each with an `inputs` object and a distinct `id`, a path of the files list with no entry, a rename checked at its old path too, while an `unchanged` status needs none and a committed `.terraform` file needs one like any other path, so a binary that reads no `.terraform` file is refused here; or a `claims-eval` reply that does not give every trigger and every claim of the files exactly one state from its list, or whose `changes` items are not a level, a case id of letters, digits, `_`, `.`, `:` or `-`, one of the 11 attributes of [verification-ladder.md](../../terraform-module-reviewer/references/verification-ladder.md#states) an `explained` flag and, when given, `explained_by`, at most 20 claim ids of the claims file on an explained change only, or whose `capped` is not the classifier's |
| `ladder refused` | The ladder record is not JSON, not schema 1, or names another head or base. `claims-eval` does not run |
| `claims refused` | `claims.json` over 64 KiB, not a JSON object, over 48 claims, or a claim id that is not `C-` and digits or appears twice. `claims-eval` does not run |

A not-run behaviour step is an unknown at [verdict.md](verdict.md#behaviour-evidence) rule 4. `review-run.sh ladder --not-run <token>` writes the same object with the reason `ladder not run: <token>` and runs no evaluation ([review-run.md](review-run-details.md#steps-not-run)). Nothing is guessed in its place. Exit 2 is a usage error: a relative path, `eval` before `classify`, or an out directory that already holds the step's files.

## The Record

`record.txt` joins the verification record in the [handover](github-io.md#handover). Its lines, in order:

```text
behaviour: ran, <n> triggers, <c> over the cap[, inert]
trigger <id> `<file>` line <line> <category>: <state>[, wrapper <derived|copied>][, complete][, unexercised][, identical][, outstanding <n>, digest <64 hex>]
claim <claim_id> on <trigger id> at <base|head>, <predicate_type>: <state|discarded>
change <trigger id> <level> case <case> <attribute>: <explained[ by <claim ids>]|unexplained>
```

or the one line `behaviour: not run: <reason>`. File paths are relative to the module root, as the reviewer's diff is, in a code span; a trigger with no line has no `line` part. A trigger line says `complete` when `claims-eval` gives `complete` true, and the number of its outstanding differences with their `evidence_digest` when it gives both; the outstanding ids are `<trigger id>|<level>|<case>|<attribute>` of that trigger's `unexplained` `change` lines, which the reviewer names in a finding's `explains` with the digest ([verdict.md](verdict.md#behaviour-evidence)). One `change` line per difference between base and head that `claims-eval` reports, never with the case's inputs; an explained one names the claims `claims-eval` gives in `explained_by`, at most 20 ids of the claims file, so a pass can be traced to the claims behind it. A claim's node, revision and predicate are printed only when each matches its closed pattern, since the model wrote the claims file; otherwise the line is `claim <claim_id>: <state>`. No reason text from the tool and no expression crosses: the reviewer reads the trigger's file and line itself.

## The Run Object

`run-behaviour.json` is the run file's optional `behaviour` key for [render-comment.sh](render-comment.sh):

```json
{"status": "ran", "reason": null, "capped": 0,
 "triggers": [{"id": "T-001", "file": "main.tf", "line": 2, "category": "wrapper-change", "state": "unverifiable"}],
 "claims": [{"claim_id": "C-1", "state": "unverifiable"}]}
```

A trigger carries `complete`, `outstanding` and `evidence_digest` when `claims-eval` gives them, copied as they are and held to their grammar: `complete` a boolean, `outstanding` at most 256 ids of this trigger matching `^T-[0-9]{3}\|L[1-4]\|[A-Za-z0-9_.:-]{1,64}\|[a-z_]{1,32}$`, sorted and each once, and `evidence_digest` 64 lowercase hex characters, only with an outstanding id; a `verified`, `covered` or `inert` trigger carries neither. A trigger carries `unexercised: true`, and its record line `, unexercised`, when its state is `unverifiable` with no `complete`, `outstanding` or `evidence_digest`, the plan coverage (L4) is its only level, its `change_kind` is `added`, its category and every merged category is `dynamic-block-change` or `unclassified-change`, its attribute is not a meta-argument (`provider`, `count`, `for_each`, `depends_on`, `lifecycle`, `provisioner`, `connection`), and its address is a managed resource address, `[module.<call>.]<type>.<name>` with optional index keys and a type with an underscore, so never `var.`, `local.`, `output.`, `data.`, `provider.` or `terraform`. Its value must read one variable the change adds with a null default and nothing else: no contextual reference, one referenced input, and the value exactly `var.<name>`, or for a dynamic block `var.<name> == null ? [] : [...]` or `var.<name> != null ? [...] : []`. The variable must be one the change adds in the trigger's own directory: `classify` writes `nullvars.json`, `{dir, name}` of each such variable. When `mtf-facts version --json` lists both `behaviour.declarations` and `behaviour.schema-required`, the entries come from the report: a `var.<name>` trigger the change adds whose `declaration` has `added` true, `default` `"null"` and `nullable` `"unset"`, each field read on its own, so a field the report adds later changes nothing; a trigger with no `declaration` gives no entry. With a provider schema, `required.json` is then the `<type>.<path>` of every trigger whose `schema_required` is not exactly `not_required`, so `unknown` and an absent field require it, and the trigger's own path is always on the list it is checked against. A binary without both features, or whose `version --json` fails, takes the path below, where a variable's head block, read from the clone as text at the classifier's line and never run, a small tokenizer accepts. It accepts only this form: per line, quoted strings removed first, escape-aware; no string holding `${` or `%{` and none left open; then no `${`, `%{`, `<<`, `#`, `//`, `/*` or `*/`; depth counted over `{}`, `[]` and `()`, the block ending where it returns to zero within 200 lines; exactly one `default` attribute at depth 1, whose value is exactly `null`; and no `nullable` attribute at depth 1. A `default` deeper in is part of the type. Every other block, a link, a file that resolves outside the module root or is over 2 MiB, the facts engine's file size cap, gives no entry; the tokenizer is no HCL parser, and what it accepts is the whole of what it claims. Marking also needs a provider schema: `classify` writes `required.json`, each attribute the schema marks `required` and each block with `min_items` above 0, at every block depth, on a type a trigger names. A type the schema does not hold is written `<type>.*` and requires everything of it. An attribute or block on that list, at the trigger's full attribute path with every `dynamic` segment dropped, is never marked, since it takes no null; a schema it cannot read, a list that is not a list of strings, and a run with no schema require everything, so nothing is marked. The trigger of such a variable, with no level, is marked too when every trigger it follows is marked.  The trigger's directory must be one terraform read at the head: a planned example is that directory, or calls it directly through a module call whose source resolves to it, so the head's variable block and argument were type-checked with the variable unset; a directory loaded only through another module is not seen and is not marked. The plan side must be known whole: the ladder record's coverage is `complete` every example's head is `planned` or `planned-no-changes` with between 1 and 999 addresses and at least one module call, and no planned address, index keys removed, equals the trigger's address or ends in `.` and it, so a resource an example creates at any module depth leaves it unmarked. When in doubt there is no mark; the render reads it ([verdict.md](verdict.md#undemonstrated-features)). A trigger carries `identical`, the examples a plan diff found the same, repository-relative, sorted, at most 20, and its record line `, identical`, when its state is `unverifiable` with no `complete`, `outstanding` or `evidence_digest`, it is not marked `unexercised`, its `change_kind` is `added`, and it is on the closed list: a variable (`var.<name>`, `unclassified-change`) with no level, so with no `validation` block, which could fail a caller that never sets it, or an argument or block of a managed resource address whose only level is L4 and whose categories are `unclassified-change` or `dynamic-block-change`, not a meta-argument, with no contextual reference and one referenced input, in the value shape `unexercised` reads: exactly `var.<name>`, or a dynamic block null-guarded on it, where `<name>` is a variable the change adds in the same directory with a null default (`nullvars.json`). A dynamic block of such a resource, the only category `dynamic-block-change`, whose `for_each` is exactly `var.<name>`, where `<name>` has a map, list or set type, is on the list too when the change adds `<name>` in the same directory with no level and a literal default, as a `var.<name>` trigger with `change_kind` `added`, `levels` `[]` and a `declaration` with `added` true and `default` `literal` shows, and nothing is over the classifier cap. A variable with no level has a null, `{}`, `[]` or scalar default and no `validation` block, and only `{}` or `[]` plans with a `for_each`, so at the default the block makes no block, whatever input an existing caller sets. An object type is not: `{}` converts to an object whose optional attributes take their defaults, and `for_each` iterates its attributes, so it makes a block. A trigger at the same address that names no attribute, or a block of the same type, that the change edits or removes, such as a static block made dynamic, keeps the block off the list: the engine reads the `for_each` alone, and the content may read existing inputs. A nested dynamic block is not on the list. A module call argument is never on the list: the plan shows it only through the child, where a value the child joins to an unknown one can hide it. Nor is an output: the engine takes an added output to L1. `--plan-diff` names the coverage file of [verify-pass.md](verify-pass.md#plan-coverage), whose `plan_diff`, with its merge base module calls, moves into the module root frame as the coverage does; a file outside its shape is no evidence. The coverage must be `complete`, with every example's head `planned` or `planned-no-changes` and between 1 and 999 addresses and at least one example with head module calls, which a hosted record does not carry, and the trigger must sit in no example directory. An example counts by the HCL the plan diff compared: one whose plan diff is `equal` and whose merge base module calls call the trigger's directory is eligible; one absent at the merge base, or `equal` and not calling it, is not; any other example that calls it at the head, or whose files the change touches, leaves the trigger as it was. At least one is eligible, and one of them plans the address the change sits in under its call (`module.<call>.`): the resource for an argument, any address of the module instance for a variable. The render reads it ([verdict.md](verdict.md#identical-plans)). A trigger the classifier merged from others carries their categories as `also_categories`, copied from the classifier output, each a category of the list once. Output outside that grammar is `output refused`. A trigger's `state` is `inert`, `verified`, `covered`, `refuted` or `unverifiable`; a claim's is `verified`, `refuted` or `unverifiable`, and a claim the tool discarded is `unverifiable`. A not-run object has its `reason`, no trigger, no claim and `capped` 0. A refuted trigger or claim blocks at ladder rule 2 by itself. The render lists every unverifiable trigger and claim, the capped count and a not-run step in section 5 of [comment-format.md](comment-format.md#section-order), counts each as a gap, and writes the evidence line under the rationale; a trigger the host computes as `reported`, `tested`, judged by Check A or undemonstrated ([verdict.md](verdict.md#behaviour-evidence)) is no gap.

## Wrapper Versions

The `terraform_wrapper_module_for_each` hook of `antonbabenko/pre-commit-terraform` writes each wrapper `versions.tf` from its module's `versions.tf`. Before v1.89.0 it writes a fixed template. From v1.89.0 it copies the file unchanged. From v1.106.0 on it copies it and deletes the `user_agent` and `module_name` attributes of each `provider_meta` block. A maintenance pull request that moves the hook across that version regenerates the wrappers, and no level of the ladder can verify a `provider_meta` edit. The host computes the hook's output itself, runs nothing from the clone and trusts no check result.

`behaviour-pass.sh wrappers --clone <Step 3 clone> --head <headRefOid> --diff <files.json> --prefix <module root prefix> --out <dir>` writes `<dir>/wrappers.txt`, one line per wrapper `versions.tf` the files list names under the module root: its module-relative path, a space and its result. The pairs are the pull request fix skill's ([write-path.md](../../terraform-module-pr-fix/references/write-path.md#wrapper-versions)): `wrappers/versions.tf` comes from `versions.tf`, and `wrappers/<sub>/versions.tf` from `modules/<sub>/versions.tf`, where `<sub>` is one name of at most 64 characters of letters, digits, `.`, `_` and `-` that starts with a letter, a digit or `_`. Nothing else is read.

It reads three files at the head: the wrapper, its module file and the repository's `.pre-commit-config.yaml`, each with `ls-tree` and `cat-file blob` run under the environment and `-c` options of the form in the reviewer's [git-safety.md](../../terraform-module-reviewer/references/git-safety.md#the-form). The form's table of queries lists neither subcommand: like the base extraction of the reviewer's [facts-engine.md](../../terraform-module-reviewer/references/facts-engine.md), these two read objects only and run no driver, filter or textconv. A partial clone is refused, since git would fetch its missing objects. The depth-1 clone serves: a blob of the head needs no history. A file counts only when it is a `100644` blob of at most 64 KiB whose ancestors are tree entries.

The pin is the `rev` of the one `- repo:` entry of `https://github.com/antonbabenko/pre-commit-terraform` that lists the hook, read line by line as data. The reader fails closed rather than parse YAML: the file is no evidence when it holds a form a YAML loader could read another pin from. Those forms are a backslash anywhere, which covers an escape in a quoted scalar; a quote left open at the end of a line; a block scalar indicator (`|` or `>`); a flow mapping, or a flow sequence not closed on its own line; an anchor, alias, tag, merge key or complex key; a line that is not a comment, a blank, a list item or a key with a space after its colon, such as a plain scalar continued onto the next line or a `---` or `...` document marker; a `repos` key that is not the one key at column 0, nested or repeated; a `rev` indented otherwise than the keys of its entry; a `#` in a value with no blank before it, such as `v1.106.0#x`; a `repo` or `rev` key in any other spelling, such as a second `rev` key or a value on the next line; a `repo` URL outside a plain `https` form, such as one with a percent escape; and the repository name `pre-commit-terraform` or the hook id named a second time, in any letter case and under any owner or host. The `repo`, `rev` and hook `id` keys are read only with a space after the colon. A one-line flow sequence, such as `args: [--fix=lf]`, is read. A `--module-repo-provider` option anywhere moves the hook to another provider, and the file is no evidence. A `rev` of the form `v<x>.<y>.<z>` at v1.106.0 or later expects derive(module), the function in [wrapper-derive.pl](wrapper-derive.pl) both skills run. A tag from v1.89.0 up to v1.106.0 expects the module file byte for byte. An earlier tag gives `unknown old hook`, since that hook wrote a fixed template. A version with no `v`, such as `1.106.0`, names no tag of the repository and is unreadable. The hook strips the attributes only in the `provider_meta` block of its provider, `aws` by default, while derive strips them in every block, so at v1.106.0 or later a module file with any other `provider_meta` line is no evidence.

| Result | When |
|--------|------|
| `derived` | The pin is v1.106.0 or later and the wrapper equals derive(module) |
| `copied` | The pin is v1.89.0 or later and before v1.106.0, and the wrapper equals the module file |
| `differs` | The wrapper is not the expected file |
| `unknown <reason>` | No expected file: `no pin` (no file or no entry), `pin not a release tag` (a branch or a commit), `old hook` (before v1.89.0), `hook not listed`, `hook options`, `pin unreadable` (any of the forms above, two entries or `rev` lines, a byte outside printable ASCII), `provider_meta`, `derive undefined`, `wrapper <why>` or `module <why>`, where `<why>` is `link` (the file or an ancestor), `not a regular file`, `absent`, `over size` or `read failed`; `partial clone`; `read failed` |

`eval --wrappers <file>` reads the file only when it has at most 256 lines, each in that grammar; any other file is no evidence. A trigger whose file is a wrapper with `derived` or `copied`, and whose state is `unverifiable`, becomes `inert`, with no outstanding difference and no `change` line, and its record line says `, wrapper derived` or `, wrapper copied`. A `differs` or `unknown` wrapper and a `refuted` trigger keep their state. `review-run.sh handover` reads it the same way and states each line as `Wrapper versions: <path> <result>` in the task's own text, before the untrusted block, where the reviewer's [Check E](../../terraform-module-reviewer/references/check-e-profile.md#reads-fails-when-and-severity) reads it. The judgment variant's prefix ([facts-variant.md](facts-variant.md)) is at its size cap and carries only Check E's pointer line, so a judgment run takes `derived` and `copied` as no finding, and judges a `differs` or `unknown` wrapper by the generated content rules alone.

## Caller Code

`mtf-facts` marks a `literal-argument-change` trigger `caller_code` when the changed argument is a literal in a `.tf` file below `examples/` or `tests/` that the change modifies in place, and `claims-eval` then reports it `inert` with the reason `a literal argument of caller code under examples/ or tests/; no module user runs it`, unless a claim of it is refuted. The classifier makes the mark only after it has sealed those two directories: it reads the tree it was given, and no configuration of that tree outside them may load them as a module. Anything it cannot place, such as a read site it cannot resolve, a source that is not a plain registry address or a local path, a Terragrunt or OpenTofu file or a `.gitmodules` file, withholds the mark, and the trigger stays unverifiable as before. The seal reads no test file (`.tftest.hcl`) and no configuration of another tool, and it reads only the tree it was given.

Under a module root prefix that tree is one directory of the repository, and a root configuration outside it, such as a root example or a test run, may load the example it holds. The seal cannot see that, so `eval --prefix` drops the reading: a trigger the tool reports `inert` whose classifier entry has `caller_code` true becomes `unverifiable`, with no outstanding difference and no `change` line, and its record line says `unverifiable`. A `refuted` trigger stays refuted, a trigger the tool reports `inert` without the mark stays inert, and a wrapper the pass makes inert ([Wrapper Versions](#wrapper-versions)) keeps that state. With no prefix, or an empty one, the tool's reading stands. A `caller_code` value that is not a boolean is `output refused`. The mark crosses to no run trigger and no record line.

This changes the all-inert reading of plan coverage ([verdict.md](verdict.md#the-ladder)). A change whose only triggers are literals of example or test code, with no prefix, has every trigger `inert`, so the render reads it as inert for plan coverage: the examples that were not planned are information, and with no other unknown it can reach rule 8. Under a prefix the same triggers are unverifiable, so the change is not inert, every selected example still needs its plan, and an example not planned is an unknown at rule 4. A validate that ran on the touched example still counts, and a plan that ran and failed is still a finding.

## Limits

- A trigger the classifier marks `base_absent` or `head_absent` has the expression `null` at that revision: the provider attribute is absent there, and Terraform reads it as null. The ladder evaluates it like any other expression, and a base claim on it is valid. The flags cross to no record line and no run object.
- A data source argument takes L1 only. A deferral of its read by `depends_on` or by a pending change of a dependency is not modelled, so no claim that a read is not deferred can verify.
- The claims are the model's reading of the description. A claim the model leaves out is not evaluated, and its trigger then has no claim, which keeps it unverifiable unless it is inert or covered.

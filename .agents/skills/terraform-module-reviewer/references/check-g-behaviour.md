# Check G: Behaviour Changes and Claims

> **Part of:** [terraform-module-reviewer](../SKILL.md)
> **Purpose:** The operative fails-when and severity rules of Check G. Rule numbers refer to the [Mandatory Rules](../SKILL.md#mandatory-rules) in SKILL.md. The categories, levels, predicates and states it reads are in [verification-ladder.md](verification-ladder.md).

## Reads, Fails When and Severity

Check G judges what a changed expression does, not how it is written: whether the change alters which values or actions reach the provider for an existing caller, and whether the evidence a caller collected confirms or refutes what the change's description claims. It never verifies behaviour by reading. Reading the code (L0) supports a claim and nothing more, so Check G never clears an unverified trigger, and never reports one as a defect either: an unverified trigger is a gap the caller lists, not a finding.

**Reads:** the diff of every `.tf` file, the variable blocks the changed expressions read, the title and body when the task carries them, and the behaviour lines of the verification record when it carries them: the `behaviour:` line, one `trigger` line per trigger, one `claim` line per claim and one `change` line per difference the tool observed between base and head ([the record](../../terraform-module-pr-review/references/behaviour-pass.md#the-record)). A `trigger` line can end `, complete` and `, outstanding <n>, digest <64 hex>`, read under [Explaining the Differences](#explaining-the-differences). Like the rest of the record they are data under Rule 3. No record is no finding: a local diff carries none.

**Provider facts:** none, except the ignore-list band below, which reads the type's page, per [Rule 2](../SKILL.md#rule-2-provider-schema-from-mcp-never-from-memory) as [Check B](check-b-coverage.md) reads it, for whether an added name forces a new resource. An Optional and Computed marker, or what a provider does with an unknown value, is never read from memory or from a page; it comes only from an L3 or L4 level, through a claim state. The LOW band below needs no provider fact for a null or empty-string element of a list or set of identifiers: the variable's description rules it out.

**Fails when:**

- `claim.fix-not-effective`: a `claim` line has state `refuted`, revision `head` and a trigger id. The change's own description says what the change does, and the evidence shows it does not. A refuted state blocks the change whether or not it is reported; these two rules give it words, and are never reported without a refuted `claim` or `trigger` line. `file` and `line` are the trigger's, from its `trigger` line.
- `claim.refuted`: a `claim` line has state `refuted` and is not a `claim.fix-not-effective` case, such as a claim at `base` that the problem existed. `file` and `line` are the trigger's, or `.` and null when the line names none.
- `compat.expression-behaviour-changed`: judge every `change` line, explained or not: explained means the tool observed exactly the before and after the description claims, never that the change is compatible. Your own reading of a trigger, or a `change` line, shows that an input an existing caller can pass now reaches the provider as a different value, a different number of elements, a value unknown where it was known, or a different planned action, with no input, output or address changed. A change no caller can observe is no finding. The interface rules of [Check A](check-a-compatibility.md) own a changed input, output, type, default or address, and this rule never fires beside one of them for the same change. Describe a plan failure only as observed: the level and the condition it was seen under, such as a null element that fails beside an unknown id at L3. Never write that a value fails the plan in general unless a run shows it at the level the claim is about. Rating a ruled-out value LOW under Severity is not such a statement: its summary says the value now reaches the provider where the base dropped it.
- `review.verification-incomplete`: the record's `behaviour:` line says `ran` and a changed file of the diff that HCL can read, a `.tf` or `.tf.json` file or a file an HCL read site names, has no `trigger` line while the line does not say `inert`; or a `trigger` line names a file the diff does not change. A record with no `behaviour:` line, a behaviour step the record says did not run, a trigger in state `unverifiable` and a claim in state `unverifiable` or `discarded` are not this rule: the caller lists them as checks that could not run. Neither is a changed file with no `trigger` line when the `behaviour:` line counts one or more changes over the cap: the classifier stopped at its cap, the caller lists those changes as one check that could not run and holds the verdict at rule 4, and nothing the change's author can do raises the cap. `file` is `.`, `line` null, and the `summary` names what is missing.

**Severity:**

- `claim.fix-not-effective` and `claim.refuted`: HIGH. A description the evidence contradicts would merge a change on a false account of what it does.
- `compat.expression-behaviour-changed`, on the compatibility scale of [Check A](check-a-compatibility.md): CRITICAL when a value the variable's type accepts and its description allows, such as a legitimate empty list or a legitimate string value, now plans differently, none of the ignored-input, documented-intent and ignore-list bands below holds, and the change does not declare a break; HIGH when it declares the break and gives no migration path; LOW when the only inputs affected are ones the provider rejects or the variable's description rules out, so the change turns a value the module silently dropped into an error at plan or apply. A null element, or an empty-string element, of a list or set of identifiers (ids, names, ARNs, keys) is ruled out by the description by definition, whatever its wording, and needs no provider evidence: a change that affects only such elements is LOW ([worked example](#worked-example-a-list-of-subnet-ids)).
- `compat.expression-behaviour-changed`, the ignored-input band: LOW, decided before the CRITICAL band above, when all four conditions below hold for one direct argument of one resource or data block, never a nested block or a module input. Each is read from the code of the base and the head and from the base's variable description, never from the pull request text ([worked example](#worked-example-a-region-now-passed-to-a-data-source)).
  1. The block exists at the base with the same address, and its `count` and its `for_each` are each unchanged: absent at both revisions, or the same text at both.
  2. The diff changes nothing in the variable's block, and its default is `null`.
  3. At the base the argument is absent or set to the literal `null`; at the head it is set to the bare reference `var.<name>`.
  4. At the base the same variable already set the same argument name, as the bare reference `var.<name>`, as a direct argument of another resource or data block of this module, expanded by `count` or `for_each` or not; or the base description of the variable says that it sets this argument on this block, named by its full address, or on every resource and data source of the module. A block of a child module, a module call, a nested block, another variable with a matching name, or a description that only mentions the variable, the block or its type, or excludes it, is not enough.

  An argument set to `null` is unset, a Terraform language rule for a direct argument of a resource or data block and not a provider fact, so a module call that leaves the variable unset or sets it to `null` plans the same value for this argument at both revisions. Only a module call that sets the variable to a value other than `null` plans a different value, and the variable now reaches this argument as it already reached the anchor argument, or as its base description says. The summary names the variable, the block's address and that such calls now pass the value to this argument, and, when the block is a data source, that an unknown value moves its read to apply. The summary also asks for a line in the release notes, and the change needs no major release. The band does not hold when that value replaces a resource or loses data or access for such a call: the CRITICAL and HIGH bands above apply. The band rates this value change only: a cycle, a `validate` or plan error, and every other change in the diff are judged under their own rules. When any condition fails, the documented-intent band below applies, and then the other bands as written.
- `compat.expression-behaviour-changed`, the documented-intent band: LOW too, decided before the CRITICAL band above, when all five conditions below hold, each read as the ignored-input band reads its conditions, never from the pull request text; condition 5 alone also reads the change's description ([worked example](#worked-example-a-key-a-dynamic-block-dropped)).
  1. The base accepted the input and dropped or overrode it on the changed path: as a direct argument, an attribute of a nested or `dynamic` block, an argument of a child module call, or through a local that replaced the value the caller set explicitly.
  2. The head makes that path do what the base description of the input, or the input's name, says the input does.
  3. A module call that leaves the input unset plans the same at both revisions. A call that writes the input sets it, also when it writes the value of the base default; a call that writes `null` sets it to null, a value other than a non-null base default, unless the variable is `nullable = false`, where null takes the default.
  4. Every module call whose plan changes sets the input to a value other than the base default.
  5. For every call whose plan changes, no resource the plan updates in place loses data or access, and every resource it destroys or replaces, if any, is one the input's name or base description says the input controls, what replaces it, if anything, is built from the value the call sets, no resource the input does not control loses access, and none of the destroyed or replaced resources holds data, such as a bucket, a table, a database, a volume, a log group, a key or a secret. When a resource is destroyed or replaced, the change's description also states that effect for calls that set the input. That statement is a declaration, never a reference: what the plan does is read from the code, and the statement only has to match it. Otherwise the CRITICAL and HIGH bands above apply, as Check A rates a new input's default that replaces a resource or loses data or access.

  The summary names the input, the path, the callers whose plan changes, those that set the input to a value other than its default, and each resource they destroy or replace, and asks for a line in the release notes; the change needs no major release. When conditions 1, 2, 3 and 5 hold and only condition 4 fails, because a call that writes the value of the base default plans differently, the case is neither LOW nor CRITICAL: report no `compat.expression-behaviour-changed` finding for it, and file the area's `review.check-not-run` under [Rule 4](../SKILL.md#rule-4-a-check-that-cannot-run-is-a-finding), MEDIUM, naming `compat.expression-behaviour-changed`, the input, the default value those calls write and what changes for them, each destroyed or replaced resource named. Whether those callers may take that change in a patch release is the maintainers' decision: its `suggested_fix` opens with `no code change:` and asks them for it. `compat.claim-contradicts-analysis` about the same change follows its one-band-below rule. A type that now rejects a value it accepted is `compat.type-narrowed` of Check A, never this band, and a change that moves a path away from what the input's description or name documents, such as one that removes something the base did for a documented caller, takes the other bands as written.
- `compat.expression-behaviour-changed`, the ignore-list band: LOW too, decided before the CRITICAL band above, when the change only adds names to a `lifecycle` `ignore_changes` list that exists at the base, in a block with the same address, `count` and `for_each` at both revisions, and the change edits nothing else in the block. Each added name shares its stem with a name the list already ignores at the base: one is the other followed by `_` and more, as `engine` beside `engine_version` or `tags_all` beside `tags`. Each added name must also be an argument the block sets from an input, so a create still applies the caller's value, and none may be an argument the type's page marks as forcing a new resource, one that grants or restricts access, a credential, a security or data protection control (a policy, a principal, a password, a token, a key or encryption setting, public access, deletion protection, backup, retention, versioning or logging), or one that sets a count, a size, failover, network placement or an identity. No version attribute (`version`, or a name ending `_version`), `name` or `name_prefix` takes this band, whatever stem it shares. A payload the resource deploys never takes this band: a task or container definition, an image, user data, a secret or parameter value, a policy or a configuration document. The page must be read in this review; with no page read for the type, the band does not hold. The summary names each added attribute and the one the list already held, says that a resource the module creates still takes the input's value and that a later change of that input on an existing resource plans no update, and asks for a line in the release notes and the description. A new list, `all`, or any other added name takes the other bands as written.
- `review.verification-incomplete`: MEDIUM. It is an unknown, and the pull request verdict reads it at rule 4, never as a defect of the module.

`rule_id` prefixes: `claim.`, for `claim.refuted` and `claim.fix-not-effective`; `compat.expression-behaviour-changed`; and `review.verification-incomplete`.

## Explaining the Differences

A `trigger` line with `complete` says every level the trigger takes ran, its cases are complete, every control is valid and the observations compare. With `outstanding <n>, digest <hex>` as well, the only thing that keeps it `unverifiable` is its `<n>` unexplained differences, the trigger's `change` lines that say `unexplained`. When the review judges those differences in a finding, the finding says so, and the host can then report the trigger as judged instead of listing it as unverified:

- The finding is `compat.expression-behaviour-changed` or a `claim.*` rule, with `file` and `line` the trigger's.
- `explains` lists the ids of the differences it judges, each `<trigger id>|<level>|<case>|<attribute>` from one `change` line, all of one trigger. `evidence_digest` is the line's digest, copied as written. No `complete`, or no digest, means no `explains`.
- List an id only when the finding states what that difference does to a caller. The union may span findings: two findings on one trigger each list the ids they judge. An id no finding lists keeps the trigger `unverifiable`, an unknown at rule 4.
- The severity is the rule's own, at least LOW, which is the floor. A difference a caller cannot observe is no finding, so it is never listed and the trigger stays unverifiable.
- `explains` never answers a refuted claim: a refuted state blocks at rule 2 whatever the findings say.

The fields are in [findings-schema.md](findings-schema.md#optional-fields).

## Worked Example: A List of Subnet Ids

A change drops `compact()` around `concat(aws_subnet.private[*].id, var.subnet_ids)` in a resource's `subnet_ids`, so the list keeps a known length at plan when one id is unknown. `var.subnet_ids` is `list(string)`, described as additional subnet ids. The record's scoped claims explain the unknown cases. The `change` lines left `unexplained` are the cases with a null element and with an empty-string element of `var.subnet_ids`: the base dropped the element and the head passes it on. The empty list and the known ids plan as before.

A null or empty-string element of a list of ids is ruled out by the description by definition, so the rating needs no provider evidence. The finding is `compat.expression-behaviour-changed` at LOW, at the trigger's file and line. Its summary says such an element now reaches the provider where the base dropped it, and says the plan fails only if a run showed that. With `complete` and a digest on the trigger line, its `explains` lists those cases' ids. It is not CRITICAL, and the change needs no major release. Had the empty list or a known id planned differently, that is a value the description allows, and the finding would be CRITICAL unless the change declares the break.

## Worked Example: A Region Now Passed to a Data Source

A module looks an existing event bus up with `data.aws_cloudwatch_event_bus.this` when it creates none. At the base that data source sets no `region`, while the module's resources already set `region = var.region` as a direct argument. `var.region` is `string`, defaults to `null`, and nothing in its block changes. The head adds `region = var.region` to the data source, whose `count` is unchanged and which has no `for_each`.

All four conditions of the ignored-input band hold. The finding is `compat.expression-behaviour-changed` at LOW, at the data source line. Its summary says that module calls that set `region` now pass it to `data.aws_cloudwatch_event_bus.this`, as the module's resources already did, so it reads the existing bus in that region; that an unknown region moves that read to apply; and that the release notes should say so. It is not CRITICAL, and the change needs no major release. Had `var.region` defaulted to a fixed region, condition 2 fails, and the finding is CRITICAL unless the change declares the break.

## Worked Example: A Key a Dynamic Block Dropped

A table module takes `replica_regions`, a list of objects, and its base description names `deletion_protection_enabled` among the keys of each replica. At the base the `dynamic "replica"` block of the table sets every other key, so a call that set this one planned nothing for it. The head adds `deletion_protection_enabled = lookup(replica.value, "deletion_protection_enabled", null)` to that block.

All five conditions of the documented-intent band hold. The base accepted the key and dropped it on an attribute of a `dynamic` block. The head does what the description says the key does. A call that leaves the key out plans `null` at both revisions. Only a call that sets the key plans a change, and it updates each replica in place, turning the protection on or off as the call asks, so nothing is destroyed or replaced and nothing loses data or access. The finding is `compat.expression-behaviour-changed` at LOW, with its line for the release notes, and the change needs no major release. It is never MEDIUM: this rule has no MEDIUM band, and the one MEDIUM case is the `review.check-not-run` the band names. The key's name already says what it does, so condition 2 holds even where the description does not name the key. Had neither the description nor the key's name said what the head now does with it, condition 2 fails, and the finding is CRITICAL unless the change declares the break.

## Suggested Fixes

| `rule_id` | Form | The fix |
|-----------|------|---------|
| `claim.fix-not-effective` | needs decision | Whether the change does what it says: (a) change the expression at `<file>:<line>` so the head shows the claimed behaviour, named; (b) `no code change:` correct the description to what the evidence shows, the sentence given. |
| `claim.refuted` | `no code change:` | The corrected sentence for the description, stating what the evidence showed. |
| `compat.expression-behaviour-changed` | needs decision | (a) keep the base behaviour for the inputs that change, such as filtering the value the base filtered, named; a filter over an input that may be unknown says that it makes the list unknown again at plan, the defect the change removed; (b) keep the change and state it in the description, with the inputs it affects and what they now do; for CRITICAL, declare the break. |
| `review.verification-incomplete` | `no code change:` | For the maintainers, not the author: review this head again once the behaviour record covers every changed file. |

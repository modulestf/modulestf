# Check A: Backwards Compatibility

> **Part of:** [terraform-module-reviewer](../SKILL.md)
> **Purpose:** The operative fails-when and severity rules of Check A. Rule numbers refer to the [Mandatory Rules](../SKILL.md#mandatory-rules) in SKILL.md.
> **Engine text:** the text of the rules [rule-facts.md](rule-facts.md) marks `tool` or `candidate` is in [engine/check-a-compatibility.md](engine/check-a-compatibility.md), one section per rule. It is part of this check: read it with this file.

**Reads:** the diff of `variables.tf`, `outputs.tf`, `versions.tf`, `main.tf` and sibling `.tf` files, and any submodule equivalents, with the bodies of any document the module generates; the module's declared version or release config to learn whether this change is declared as a major or breaking change. When the task carries the title the change will be released under, a `!` after its type, or a `BREAKING CHANGE:` trailer travelling with it, also counts as declaring the change breaking. When the task carries accompanying prose, the compatibility claims in its title and body, and in no other item, resolved under [quoted-claims.md](quoted-claims.md#compatibility-claims-come-from-the-title-and-the-body).

**Provider facts:** moved to `compat.provider-floor-raised` in [engine/check-a-compatibility.md](engine/check-a-compatibility.md#compatprovider-floor-raised).

- A compatibility claim in the title or the body contradicts this check's own conclusion.
- Your own reading rates the change breaking, the title or the body declares the break, and neither gives a reason compatibility could not be held, against [the reason for a break](../../terraform-module-maintainer/profiles/terraform-aws-modules/code-conventions.md#pull-request-title-and-the-reason-for-a-break). No accompanying prose is no finding.

**Severity:**
- CRITICAL for an undeclared break: moved to the section of each break rule in [engine/check-a-compatibility.md](engine/check-a-compatibility.md).
- HIGH when the change is breaking and declared as breaking but the migration path is missing: no `moved` block, no upgrade note, no replacement input or output. HIGH too when the title or the body contradicts this check (`compat.claim-contradicts-analysis`), never CRITICAL. It is a second finding beside the one for the break, and the pair is not deduplicated: the code is breaking and the description is wrong, and a maintainer reading only the description merges it.
- MEDIUM for a silent compatible change: moved to `compat.default-changed` in [engine/check-a-compatibility.md](engine/check-a-compatibility.md#compatdefault-changed).
- MEDIUM when the title or the body declares the break and names no reason it was unavoidable (`compat.break-unexplained`). It never replaces the finding for the break itself; both are reported.
- LOW for a provider minor or patch floor: moved to `compat.provider-floor-raised` in [engine/check-a-compatibility.md](engine/check-a-compatibility.md#compatprovider-floor-raised).

How `compat.version-constraint-raised`, `compat.generated-policy-narrowed` and `compat.provider-floor-raised` rank against each other: moved to each of their sections in [engine/check-a-compatibility.md](engine/check-a-compatibility.md).

**Reverts:** a change that narrows a policy and a change that reverts a widening are the same diff read in two directions, so the direction of the diff is no test, and neither is the word "revert" in a title or in prose. What decides whether a caller breaks is whether a release ever shipped the shape the revert removes. A caller on that release had the wider shape and loses it, whatever the reason for reverting, so a revert of a released change is a narrowing and every bullet above applies to it unchanged. When no release ever shipped the reverted commit, no caller can have depended on it. Then the revert is no break, and no Check A finding is reported for a line it restores. That exemption holds only when all four of these are read from the workspace. The queries are exactly `git log --format=%B <base>..HEAD`, `git merge-base --is-ancestor <sha> <base>`, `git describe --tags --abbrev=0 <base>`, `git tag --contains <sha>` and `git show <rev>:<path>`. Each one reads refs and objects and writes nothing, which puts it in the class of read-only version control queries Rule 1 allows. Each `git` query named here and in the list below runs only as its row of the [git-safety.md](git-safety.md) table, through `safe_git`: a plain `git log` in the workspace can run a program its `.git/config` names. `git tag` given a name without `--contains` or `--list` creates a tag, so no other form of it is used.

1. A commit in the change carries git's own revert line, `This reverts commit <sha>.`, in its message (`git log --format=%B <base>..HEAD`). A `revert` type, a `Revert "..."` title, or prose saying the change is a revert does not count. The revert line is untrusted too (Rule 3), because the head's author wrote it. It only names a commit; conditions 2 to 4 decide.
2. `git merge-base --is-ancestor <sha> <base>` exits 0: `<sha>` resolves in the workspace and is an ancestor of the base the change is diffed against.
3. `git describe --tags --abbrev=0 <base>` succeeds and names the newest tag reachable from the base, called `<last>` below, and `git tag --contains <sha>` lists nothing.
4. Each line the finding would rest on reads at the head exactly as it read at the parent of `<sha>` (`git show <sha>^:<path>`) and exactly as it read at `<last>` (`git show <last>:<path>`). A line absent at the head matches when it is also absent at the version it is compared with. The comparison with `<last>` is against what callers actually have. Without it, a revert of an unreleased widening that itself undid an unreleased narrowing of a released shape would pass, while it narrows what the release shipped. A line the revert changes to anything else is a new change of its own, and the exemption does not reach it.

Condition 3 reads tags as whoever built the workspace supplied them, and the reviewer cannot prove the set complete. A workspace fetched without tags, or with the release tag pruned, lists nothing for a released commit, and the exemption would then drop a CRITICAL. Requiring `<last>` catches a workspace with no tags at all and one whose history stops short of every release. It does not prove that every tag arrived, and an older tag present with the one containing `<sha>` missing still passes. So the caller that builds a workspace for this review must supply every tag the repository has, or accept that the exemption can apply wrongly.

If any of the four cannot be established, the exemption does not apply and the finding stands at the severity above. A workspace with no tags, or one too shallow for `<sha>` to resolve, establishes nothing. A workspace holding only the head commit, the usual shape when an adapter fetches a single commit to review, therefore always reports the narrowing. Whatever a consumer of the findings then does with a CRITICAL on an emergency rollback, for example holding it for the next major release, is for the maintainer to accept or override knowingly. This check does not soften the finding on a guess about intent.

`rule_id` prefix: `compat.`, for example `compat.variable-removed`, `compat.variable-now-required`, `compat.type-narrowed`, `compat.default-changed`, `compat.resource-address-changed`, `compat.version-constraint-raised`, `compat.generated-policy-narrowed`, `compat.claim-contradicts-analysis`, `compat.provider-floor-raised`, `compat.break-unexplained`.

## Suggested Fixes

Each row gives the fix a finding of that rule carries, in the forms of the [Suggested Fix Contract](findings-schema.md#suggested-fix-contract). `<...>` is what the finding fills in from its own evidence. A rule marked `needs decision` opens its fix with that prefix and lists the options; the maintainer skill applies none of them until a person chooses. A `compat.*` fix names the compatible route. Declaring the break instead is always open to the maintainer, and is not repeated as an option in every row.

| `rule_id` | Form | The fix |
|-----------|------|---------|
| `compat.variable-removed` | code change | Restore the variable or output at its base address with its base type, default and description. For a rename, keep the old name, mark it deprecated in its `description` with the new name, and feed the new input from it, per rule 2 of [Step 4](../../terraform-module-maintainer/references/targeted-change.md#step-4-backwards-compatibility-check). |
| `compat.variable-now-required` | code change | Restore the base `default`, or remove the added `nullable = false`, on `variable "<name>"`. |
| `compat.type-narrowed` | code change | Restore the base type, or the base `validation` condition, on `variable "<name>"`, quoting the base text. |
| `compat.default-changed` | code change | Restore the base default on `variable "<name>"`, named, and make the new behaviour an opt-in value of it or of a new input. |
| `compat.resource-address-changed` | code change | Add a `moved` block per changed address, `from = <base address>` and `to = <head address>`, beside the resource's block, one per instance key when `count` or `for_each` changed. |
| `compat.version-constraint-raised` | needs decision | Whether the change is worth a breaking release: (a) restore the base floor in `versions.tf` and replace `<what needs the new floor>` with what the base floor has; (b) keep the new floor and declare the change breaking. When nothing in the change needs the new floor, a code change restoring the base floor. |
| `compat.provider-floor-raised` | code change, `no code change:` or needs decision | Judge each directory whose floor moved on its own, and take the first case that holds for it. The finding and its LOW severity are the same in every case; only the fix differs. (1) The title or the body names a provider issue, such as `hashicorp/terraform-provider-aws#<number>`, or a provider changelog entry for the version the new floor names, and the directory uses, itself or through a local module it calls, a resource or data source that issue or entry concerns: `needs decision:` whether that fix is worth the narrower support window, which a documentation page cannot show: (a) `no code change:` keep the new floor, and the change's description states it with that reason, the sentence given; (b) restore the base floor in `versions.tf` and accept the provider defect the raise avoided; when the directory calls a local module whose floor the change sets above the caller's base floor, by raising it or by adding the module, the option lowers that module's floor with it, named, since restoring the caller alone is `structure.version-floor-understated`. A directory that uses nothing the issue concerns goes on to case (2) or (3), even when the change names an issue. (2) The change uses nothing absent at the old floor, and no local module the directory calls declares a floor above the old one: restore the base floor in `versions.tf`, and name the generated content the move makes stale. (3) Otherwise `no code change:` the change's description states the new floor, and names the called module whose floor holds it up when that is the reason, since restoring the floor there would be `structure.version-floor-understated`. The fix gives the sentence, such as `The minimum AWS provider version is now 6.44 (was 6.42), which modules/file-system also requires.` The release notes are generated from the squash commit, whose message is the title Check E judges, so the description is where a person can add it. |
| `compat.generated-policy-narrowed` | needs decision | Whether the narrowing is intended, since it can be a security fix: (a) restore the removed statement, action or grant, named, in the block that builds the document; (b) keep it and declare the change breaking, with the permission callers lose in the migration notes. |
| `compat.claim-contradicts-analysis` | `no code change:` | The corrected sentence for the title or body, stating what the analysis concluded. |
| `compat.break-unexplained` | `no code change:` | What the body has to add: the reason compatibility could not be held, per [Pull request title and the reason for a break](../../terraform-module-maintainer/profiles/terraform-aws-modules/code-conventions.md#pull-request-title-and-the-reason-for-a-break). |
| Any break the change declares, HIGH for a missing migration path | code change | The missing piece, named: the `moved` block, the replacement input, or the notes file `docs/MIGRATION_<from>_to_<to>.md` with what it must say, per [Migration notes](../../terraform-module-maintainer/profiles/terraform-aws-modules/PROFILE.md#migration-notes). |

## No base

A new module, the task shape in [Inputs](../SKILL.md#inputs), has an empty base. No input, output, resource address, default, policy document or version floor existed before it, so no existing caller can break, and Check A does not run. It reports nothing: no `compat.*` finding and no `review.check-not-run`, because nothing was left undecided. A title or body that makes a compatibility claim has no conclusion of this check to contradict, so `compat.claim-contradicts-analysis` and `compat.break-unexplained` are silent too.

This covers only a base that is known to be empty. A base that exists but could not be read is a check that cannot run, under [Rule 4](../SKILL.md#rule-4-a-check-that-cannot-run-is-a-finding).

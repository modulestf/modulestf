# Rule Summaries

> **Part of:** [terraform-module-reviewer](../SKILL.md)
> **Purpose:** One plain sentence or two for each `rule_id`, written for people who never read the check files. The modules.tf rules page is built from this table and [rule-facts.md](rule-facts.md). Nothing in the review reads it: each rule's operative text stays in its check file.

`tests/skills-test.sh` checks that this table has exactly one row for every `rule_id` in [rule-facts.md](rule-facts.md), no other row, and a summary in each. A rule added, renamed or removed in the registry changes this table in the same change.

| `rule_id` | Summary |
|-----------|---------|
| `claim.fix-not-effective` | The change description says what the fix does, but verification runs against the changed code show it does not. Merging it would ship a change on a false account of its effect. |
| `claim.refuted` | A claim in the change description, such as that the problem existed before the change, is contradicted by verification runs. A maintainer would merge on a false account of the change. |
| `compat.break-unexplained` | The title or description declares a breaking change but gives no reason compatibility could not be kept. Users facing the break are not told why it was unavoidable. |
| `compat.claim-contradicts-analysis` | The title or description makes a compatibility claim, such as "the only change is X", that the review's reading of the code refutes. A maintainer who reads only the description would merge a break. |
| `compat.default-changed` | A variable's default changes, or a removed `data` block changes a value callers see. Callers who edit nothing get different resources or values after upgrading. |
| `compat.expression-behaviour-changed` | A changed expression sends the provider a different value, element count or planned action for input an existing caller can pass, with no input, output or address changed. The caller's plan changes unasked. |
| `compat.generated-policy-narrowed` | An IAM, bucket or similar policy the module builds loses or narrows a statement, action or grant. Callers with an unchanged configuration lose a permission, though nothing fails at plan or apply. |
| `compat.provider-floor-raised` | The minimum provider version rises by a minor or patch release. Callers on older provider versions can no longer use the module, so the narrower support window belongs in the release notes. |
| `compat.resource-address-changed` | A resource is removed, renamed or moved to a new address, for example into `for_each` or a submodule, with no `moved` block. Existing state then plans a destroy and a create. |
| `compat.type-narrowed` | A variable's type is narrowed, or a `validation` block is added or tightened, so input that was valid before is now rejected. Existing callers can fail at plan. |
| `compat.variable-now-required` | A variable loses its `default`, gains `nullable = false` or otherwise becomes required. Every caller that did not set it fails at plan. |
| `compat.variable-removed` | A variable or output is removed or renamed. Every caller that sets or reads it fails at plan. |
| `compat.version-constraint-raised` | The Terraform `required_version` floor rises, or a provider minimum moves to a new major version. Callers on the old versions can no longer use the module. |
| `coverage.argument-above-min-version` | The change adds an argument the latest provider has but the module's declared minimum provider version lacks, and leaves that minimum unchanged. Callers on the minimum version fail. |
| `coverage.attribute-not-output` | A new resource has a stable, useful computed attribute that no output exposes, or an output yields no value in a mode the module supports. Callers cannot read the value, or index an empty element. |
| `coverage.block-attribute-mismatch` | An argument is set with `name = ...` attribute syntax where the provider documentation calls it a block. The configuration is invalid and no caller can apply it. |
| `coverage.default-for-required-argument` | The module defaults an input that feeds an argument the provider marks Required, and the default is the more permissive value or contradicts the provider documentation. Callers get it without choosing. |
| `coverage.deprecated-argument` | The change starts setting an argument the provider schema marks deprecated. The module takes on a setting the provider documentation says to replace or drop. |
| `coverage.enum-value-unknown` | A literal in the module or an example falls outside the values the provider documentation lists for that argument. Either the literal or the documentation is stale, and the review asks which. |
| `coverage.mutual-exclusion-unguarded` | Two arguments the provider documents as mutually exclusive can both be set at once, with no `validation` or `precondition` to stop it. Callers who set both get a provider error, not a clear module message. |
| `coverage.optional-argument-unexposed` | A new resource has an optional provider argument that is neither exposed as a module input nor documented as a deliberate omission. Callers cannot set it. |
| `coverage.required-argument-unreachable` | An argument the provider marks Required has no module input and no fixed value that can set it. The block fails at plan for every caller. |
| `coverage.unknown-argument` | A `resource` or `data` block sets an argument the provider schema does not have, or repeats a block past its documented limit. No caller can apply it. |
| `examples.argument-undemonstrated` | The change adds an argument inside a block an example already sets, but no example sets the new argument. Users copying the examples never see it in use. |
| `examples.custom-input-required` | An example needs `-var`, a var file or a manual edit before `terraform apply` runs, such as a required variable with no value. Examples must apply as written; credentials do not count. |
| `examples.disabled-call-missing` | The complete example has no `module "disabled"` call with `create = false`. The terraform-aws-modules layout requires that call in every complete example. |
| `examples.docs-incomplete` | An example lacks its `README.md`, the documentation markers that README needs, or documents its outputs thinly. Users browsing the examples get an incomplete reference. |
| `examples.example-broken` | After the change an example cannot init, validate, plan or apply as written, for example an unsatisfied one-of or a value the AWS API rejects. Users who copy it hit the failure. |
| `examples.example-broken-at-base` | An example fails, but the same failure already happens before the change. It is reported as older breakage to fix in a separate change and does not count against this one. |
| `examples.feature-undemonstrated` | A feature the change adds, such as a new resource, nested or dynamic block, or an argument in a block no example sets, appears in no example. Users get no working configuration to copy. |
| `examples.real-domain-zone` | A changed example uses a public DNS name as an endpoint or hosted zone outside `example.com` and subdomains of `modules.tf`. Copied as is, it would point at a real domain. |
| `examples.stale-reference` | An example still reads a module input or output the change removed or renamed, or sets an input the module does not declare. The example can no longer initialize. |
| `examples.submodule-missing` | The change adds a submodule under `modules/` with no example of its own under `examples/`. Users get no runnable configuration that shows how to call it. |
| `examples.versions-missing` | An example has no `versions.tf`, or names that file differently from its sibling examples. Each example keeps its own Terraform and provider constraints in a file of that name. |
| `profile.changelog-handwritten` | The change edits `CHANGELOG.md` by hand. semantic-release writes that file from the released commits, so the edit is overwritten and the entry never ships. |
| `profile.commit-type-mismatch` | The title's type does not match the change, such as `fix` for a new input or `!` with no breaking change. The title sets the next version, so the change releases wrongly or not at all. |
| `profile.generated-content-handwritten` | A terraform-docs README region or a `wrappers/` file disagrees with the code or holds hand-written text. The next hook run overwrites hand edits, and stale rows mislead users. |
| `profile.layout-divergence` | The change adds a convention terraform-aws-modules does not use, such as a different layout for examples or submodules, or a `LICENSE` other than Apache 2.0. The module drifts from the family. |
| `profile.migration-notes-misplaced` | Migration notes for a change that forces users to act are written into `README.md`. The profile keeps them in their own file, `docs/MIGRATION_<from>_to_<to>.md`. |
| `profile.nonstandard-config-file` | The change adds or edits a `*.tf.json` file, an override file, or a `.tofu` file or OpenTofu-only block in a module Terraform can run. The family's quality gate cannot check these. |
| `profile.owner-identifier` | In a new module, a `user_agent`, README `source`, example tag URL or `--module-repo-org` hook argument names an owner other than `terraform-aws-modules`. The module would publish under the wrong owner. |
| `profile.provider-meta-missing` | A root or submodule `versions.tf` that requires `hashicorp/aws` lacks the `provider_meta "aws"` user agent naming its repository, or names the wrong one. Its AWS API calls then report it wrongly or not at all. |
| `profile.putin-khuylo-missing` | The root module creates resources without gating them on `var.create && var.putin_khuylo`, as every terraform-aws-modules root does. It still applies, but breaks a must-pass family convention. |
| `profile.region-not-allowed` | A region literal the change adds or edits is neither of the two regions the selected profile's `regions` constants allow (`eu-west-1` and `us-east-1` by default). Region names inside ARNs, hostnames or map keys do not count. |
| `profile.release-config-changed` | The change edits release or automation config the profile owns, such as `.releaserc.json` or a workflow, so that releases or checks would behave differently for every later change. |
| `profile.required-file-missing` | A new module lacks a file the terraform-aws-modules layout requires, such as `LICENSE`, a profile dotfile, one of the five workflows, or `examples/basic` and `examples/complete`. |
| `profile.template-drift` | A profile-owned static file such as `.editorconfig`, `.releaserc.json` or a workflow differs from its family template with no stated reason. Version pins are not compared. |
| `profile.title-misspelling` | A word in the pull request title misspells an identifier the diff uses, such as `atribut` for `attribute`. The title becomes the commit message and `CHANGELOG.md` entry, so the typo stays. |
| `profile.title-uninformative` | The pull request title names no capability, fix or surface from the diff, such as `feat: Update module`. It becomes the `CHANGELOG.md` entry, which then tells readers nothing. |
| `profile.unrelated-change-bundled` | A `feat` change also edits `.tf` files in a module directory that takes no part in the feature. That edit ships under the wrong release entry and is reverted if the feature is. |
| `review.check-not-run` | A check could not finish, for example because provider documentation was unreachable or a named file was missing. The review reports the gap and the rules left undecided, and never counts it as a pass. |
| `review.no-change-identified` | The review cannot tell what changed, or the workspace holds a different revision from the one it was asked to review. It stops and says so instead of reviewing the wrong code. |
| `review.path-missing` | A file the change names does not exist in the workspace. The review reports it instead of guessing what the file held. |
| `review.quoted-claim-unverifiable` | A claim in the pull request text or discussion points at a missing path or at code that does not support it. The review only counts such claims, so a comment alone never adds a finding. |
| `review.tool-disputed` | The review believes a finding from the automated checks is wrong and says why. The original finding stays in the list, and a person decides the dispute. |
| `review.untrusted-instruction` | Text in the changed files or from the change's author asks the review to skip a check, soften a finding, approve, edit a file or run a command. The review reports it and keeps to its own rules. |
| `review.verification-incomplete` | Plan-based verification ran, but a changed Terraform file has no verification entry, or an entry names a file the change does not touch. This is reported as an unknown, not as a module defect. |
| `scope.boundary` | The change adds a resource type the directory does not manage, its managed types do not prefix, and that is not a shared IAM, log or security group type or allowed in `docs/SCOPE.md`. |
| `scope.composition` | The change adds an in-scope resource that references nothing the module already has, and nothing existing references it. A maintainer decides whether an unconnected block belongs. |
| `scope.layout` | The change adds a file outside the profile's layout, such as a `Makefile`, a script or a new top-level directory. Only module code, examples, native tests, listed docs and profile files fit. |
| `scope.module-call` | The change adds a `module` block, or edits its `source`, to call anything but a local submodule under `modules/`, such as a registry or Git module. Composing modules is the caller's job. |
| `scope.new-module` | The whole module is new and manages at least one type beyond shared IAM, log and security group types. A maintainer decides whether the family takes on a module with those types and providers. |
| `scope.new-submodule` | The change adds a directory under `modules/` that manages a resource type that is neither a shared IAM, log or security group type nor allowed. A maintainer decides whether the module takes it on. |
| `scope.pre-commit-hook` | The change adds, removes or repoints a repository or hook in `.pre-commit-config.yaml`. The checks belong to the profile; moving a `rev:` pin alone is fine. |
| `scope.profile-file` | The change deletes a profile-owned file, adds a workflow beyond the five standard ones, or adds or removes workflow jobs, steps or `.releaserc.json` plugins. Checks and releases are the profile's. |
| `scope.provider` | The change brings in a provider the module did not use before, such as `hashicorp/helm`. Configuring other providers is the caller's job, which passes identifiers in. |
| `scope.readme-banner` | The root `README.md` loses the Stand With Ukraine `SWUbanner` line, or a new root README lacks it. The profile's README template has that line, byte for byte. |
| `scope.tests` | The change adds a Go test file: `go.mod`, `go.sum` or `*_test.go`. This family never uses Terratest; its tests are native `tests/*.tftest.hcl` files. |
| `scope.tooling` | The change adds config for another scanner, linter or cost tool, such as `.checkov.yaml`, `.tfsec/` or `infracost.yml`, even under `examples/`. The profile runs only its own hooks and workflows. |
| `structure.argument-order` | In a resource block the change adds or edits, `count` or `for_each` is not the first argument, or `tags` or `labels` is not the last. Every block in the module is meant to read in the same order. |
| `structure.arn-partition-hardcoded` | An ARN the change adds writes `arn:aws:`, an account ID or a region as a literal where the module could derive it. The ARN is then wrong in GovCloud, in China, or in another account or region. |
| `structure.comment-redundant` | A comment the change adds only restates what the code plainly says. It gives an experienced reader more lines to read and nothing new. |
| `structure.comment-unsourced` | A comment the change adds claims a service limitation, provider defect or ordering requirement with no official source link and no date. Limitations get lifted, and an undated claim cannot be rechecked. |
| `structure.copied-content-unattributed` | A constant copied from a document, such as an IAM policy, account ID, literal ARN or service principal, has no comment with its source URL and date. Nobody can then tell if it is still right. |
| `structure.create-flag-ignored` | A resource the change adds ignores the module's creation flag, so `create = false` no longer produces an empty plan. Callers who turn the module off still get infrastructure. |
| `structure.docs-contradict-code` | Documentation the change adds or edits, such as a README section, a variable description or an example comment, promises behaviour no code path implements. Users who rely on it get something else. |
| `structure.embedded-code-defect` | Code the module packages or reads, such as a Lambda source, that the change edits fails for an input it handles, or the fix leaves the same pattern unfixed elsewhere in the file. A defect in a changed line breaks the feature at run time; a fix that stops short is a nit the author can take now or in a follow-up. |
| `structure.feature-above-version-floor` | The change uses a Terraform language function or block newer than the module's declared `required_version`, or one only OpenTofu has. Callers on an older version the module still allows cannot use it. |
| `structure.flag-polarity` | A new feature flag's default does not match its prefix: `enable_*` or `attach_*` defaulting to `true`, or `create_*` defaulting to `false`. Existing callers then get or lose infrastructure they never asked about. |
| `structure.grouping` | A variable, output or block the change adds or moves sits outside its section, or a section header breaks the module's layout. Related inputs then no longer sit together under one header. |
| `structure.input-ignored-in-branch` | An input the change adds or forwards is read only in a branch that another input switches off. Setting it there does nothing and raises no error, so the caller thinks it took effect. |
| `structure.insecure-default` | The change weakens a secure default for encryption, public access, logging or deletion protection. Every caller who keeps the defaults gets the weaker setting. |
| `structure.missing-description` | A variable or output the change adds has no `description`. Callers and the generated documentation get no explanation of what it is for. |
| `structure.multi-provider` | The change gives the module its own aliased provider configuration, or passes one through `provider` or `providers`. The caller, not the module, should decide which regions and accounts exist. |
| `structure.output-no-try` | An output the change adds has no `try()` fallback, or its fallback changes the output's type. When the resource is not created, the output errors instead of returning null. |
| `structure.passthrough-default-drift` | A root input forwarded to a local submodule has a different default than the submodule declares for it. A caller who sets nothing gets a value the submodule does not declare, and nothing errors. |
| `structure.passthrough-field-drift` | A root input forwarded to a local submodule has different object attributes than the submodule variable. Attributes the root lacks cannot be set, and ones the submodule lacks are dropped without an error. |
| `structure.schema-shape-flattened` | A nested object input flattens or renames the structure of the provider block it feeds. The input then no longer matches the provider documentation for that resource. |
| `structure.set-index-by-position` | An expression the change adds pairs the element at a position of a list made from a set with the element at the same position of another collection. A set sorts its own way, so the pairs are arbitrary, and keys built on them move to other objects when either side changes. |
| `structure.sibling-argument-omitted` | A resource the change adds omits a routing argument such as `region` that most other resources in the file set from a module input. It can then land in a region or project other than the one the caller set. |
| `structure.sibling-block-asymmetry` | A `dynamic` block the change adds covers fewer fields than its sibling blocks or the provider schema for that block. Callers cannot set the missing fields through the module. |
| `structure.suppression-unexplained` | A comment the change adds tells a security scanner to skip a finding but gives no reason for accepting the risk. Readers cannot tell why the risk is acceptable. |
| `structure.validation-message-uninformative` | A `validation` or `precondition` the change adds has an `error_message` naming neither the accepted values or bound nor the value received. The caller learns nothing about how to fix the input. |
| `structure.validation-missing` | An input with a closed set of allowed values, such as a mode or type name, has no `validation` block or has it commented out. A typo is accepted and fails later, far from the input. |
| `structure.validation-overreaching` | A `validation` block the change adds checks another variable, enforces a compliance policy, or re-implements a service naming or format rule. A caller with a valid reason is blocked with no way around it. |
| `structure.variable-untyped` | A variable the change adds has no `type`, or uses `any` with no comment saying why. Callers get no type check on the value they pass. |
| `structure.version-floor-understated` | A `versions.tf` the change touches declares a lower version floor than the module it calls. If the two version ranges do not overlap at all, the configuration cannot initialize. |
| `structure.wrong-file` | The change adds blocks to another file when the module already has the file its layout names for them, such as IAM resources outside an existing `iam.tf`. Related code then splits across files. |

# Code Conventions

> **Part of:** [terraform-module-maintainer](../../SKILL.md)
> **Status:** The conventions that govern the code inside a module's `.tf` files.
> [PROFILE.md](PROFILE.md) owns the file set, the quality gate and the release
> process; this file owns what goes in the files.

## What this file is, and what it is not

It states family conventions. It does not teach Terraform.

How to write the construct that carries a convention - `for_each` against
`count`, a `dynamic` block, `try` and `coalesce`, `optional()` inside an object
type, `moved`, the difference between a `validation` and a `precondition` -
comes from [antonbabenko/terraform-skill](https://github.com/antonbabenko/terraform-skill),
which is the reference for the language itself. Nothing here restates it, and a
fix that turns on a construct choice names that skill rather than growing a
second Terraform manual inside a profile.

[Validation](#validation) below depends on that split holding: whether a check
belongs in a `validation` or a `precondition` is a language question, and only
the answer to it is a family convention.

Every convention below is scoped to what a change adds or edits. A module that
has diverged since 2021 is not the current pull request's problem until someone
edits that line. This is the same scoping [PROFILE.md](PROFILE.md#module-layout)
already applies to layout divergence, and it is what keeps these rules from
firing on every pull request to an older module.

## Regions

An example uses `eu-west-1`.

`us-east-1` is the one secondary region, for a case that genuinely needs a
second one: cross-region replication, a CloudFront or ACM certificate that has
to live there, a global service whose home region it is. Any other region
literal has diverged.

Where a second region is required, the fix is `us-east-1` and a sentence saying
why a second region exists at all. It is never a third region.

This is about a region the configuration chooses: a provider `region`, a `region`
argument, a module input, an example's locals. A region name that appears as a
key in a lookup map, inside an ARN, or inside a hostname is data, not a choice,
and this convention says nothing about it.

This describes what the family already does rather than imposing a preference.
Measured on 2026-09-22: `terraform-aws-lambda` examples carry `eu-west-1` 29
times and `us-east-1` 3 times and nothing else, and `terraform-aws-s3-bucket`
carries `eu-west-1` 11 times plus one `eu-central-1` in `examples/s3-replication`
- a single piece of drift in two modules.

## Configuration file formats

A module under this profile is HCL in `.tf` files.

These have no place in one:

- `*.tf.json`.
- `override.tf`, `override.tf.json`, `*_override.tf`, `*_override.tf.json`.
- A `.tofu` file, or a block only OpenTofu has - `encryption`, or `for_each` on
  a `provider` block - in a module whose `required_version` admits Terraform.

The reason for the JSON syntax is the quality gate, and it is narrower than it
first looks. `tflint` and `terraform_docs` do read a `.tf.json`, measured rather
than assumed - both were run against one on 2026-09-22 and both handled it. What
does not is `terraform fmt`: "JSON files (.tf.json, .tfvars.json, or
.tftest.json) are not modified" (`terraform fmt -help`, Terraform 1.14.4). So the
`terraform_fmt` hook, the one gate that keeps every other file in the module
consistently formatted, silently has no opinion about this one, and its diffs are
reviewed by eye alone. Against that, a module gains nothing: JSON syntax exists
for generated configuration, and nothing here is generated.

Override files carry HashiCorp's own caution against them: "Over-use of override
files hurts readability, since a reader looking only at the original files cannot
easily see that some portions of those files have been overridden"
([Override Files](https://developer.hashicorp.com/terraform/language/files/override),
read 2026-09-22). They are a local convenience, which is why
[templates/.gitignore.template](templates/.gitignore.template) already ignores all
four names. One in a repository had to be force-added past that.

The one exception that would be legitimate is a `.tf.json` generated by a tool
this profile itself runs. No such tool exists today, so the exception stays
closed until one does.

## Version floors

Two rules, both about `versions.tf` telling the truth.

### What the module uses has to exist at the floor it declares

Everything the code uses is available in every version the module's own
constraints admit. Three kinds of violation:

- A core language function or block introduced after the declared
  `required_version`.
- A provider-defined function call, `provider::<name>::<fn>`. These need
  `required_version >= 1.8`: "Provider-defined functions are supported in
  Terraform 1.8 and later"
  ([Functions](https://developer.hashicorp.com/terraform/plugin/framework/functions),
  read 2026-09-22).
- A function or block only OpenTofu has, in a module whose constraint admits
  Terraform.

Nothing catches this by running: `terraform validate` runs at the installed
version, not at the declared one, so a module pinned to `>= 1.5.7` validates
clean on 1.14 while being unusable at its own floor.

**There is no table of introducing versions here, and there should never be
one.** A table goes stale and then lies. Look the feature up in the official
documentation, which carries its introducing version, and quote that page and
the date you read it. That is the same evidence standard
[Evidence](#evidence-comments-copied-values-and-availability) asks of a comment.

The provider-argument twin of this rule lives in the reviewer's Check B as
`coverage.argument-above-min-version`, judged against the provider schema. This
one is the core language axis, judged against the configuration. They stay
separate.

### A caller does not declare less than what it calls

A declared floor is at or above the floor of everything it calls:

- the root's `required_version` and `required_providers` against each submodule
  under `modules/` the root calls;
- each example's against the module it calls, root or submodule.

[templates/versions.tf.template](templates/versions.tf.template) is copied to the
root and [templates/example-versions.tf.template](templates/example-versions.tf.template)
to both examples, with the same constraints, so a module starts with these equal. They only
drift.

A caller declaring *more* than its callee is fine and is not a divergence. An
example may legitimately need a newer provider for a resource it declares itself,
and a lower floor elsewhere is not evidence either way.

Constraint sets that do not intersect at all - an upper bound in one that
excludes the other's floor - are a different thing. That configuration cannot
`terraform init`, so it is broken rather than understated.

## Evidence: comments, copied values, and availability

Three conventions sharing one standard: a claim the reader cannot check from the
code carries its source and the date it was checked.

An acceptable source is the provider or service documentation, a GitHub issue in
the provider's or the service's repository, or an engineering post from
HashiCorp or the cloud vendor. The date is the part that matters most. The claim
most likely to rot is a limitation, because limitations get lifted, and a dated
claim can be rechecked while an undated one cannot.

### Comments

A comment exists because the code is not obvious to a senior DevOps or SRE
reader, or because a service imposes something the code cannot show. Nothing
else earns a line.

Two ways a comment fails:

- It restates what the code plainly says.
- It asserts a service limitation, a provider defect, an ordering requirement or
  any other non-obvious behaviour, and cites nothing.

Not in scope, so this does not widen later:

- Pre-existing comments. Only what a change adds or edits.
- The `####` section-header banners
  [module-structure.md](../../references/module-structure.md#section-headers)
  requires. They are structure, not commentary.
- A scanner suppression, which has its own rule in
  [module-structure.md](../../references/module-structure.md#scanner-suppressions):
  that one is about accepting a risk, this one about explaining behaviour.
- A commented-out `validation` block, which is a missing validation.

[coverage-checklist.md](../../references/coverage-checklist.md#tier-6-documentation-should-pass)
states the same thing as a checklist item: inline comments present only for
non-obvious logic.

### Copied values

A constant copied out of a document carries a comment naming the source URL and
the date it was copied. In scope:

- An IAM policy document or statement, and an SCP.
- An AWS account number, including the per-region service account IDs used for
  log delivery.
- An ARN written as a literal: a managed policy ARN, a service principal, a KMS
  alias, a layer ARN. See also [ARNs and partitions](#arns-and-partitions), which
  asks the prior question of whether it should be a literal at all.
- Any other constant whose correctness lives in a document rather than in the
  module: a service principal name, a condition key, a hosted zone ID.

The point is tracking. Every one of these changes on the vendor's schedule and
not the module's, and the only way to tell whether a literal is still right is to
know which page it came from and when somebody last looked.

The per-region ELB log-delivery account IDs are the case that proves it, and they
also show the better fix. AWS changed its own guidance for them: for regions
opened since Jakarta (`ap-southeast-3`) in December 2021 it documents a service
principal name in place of an account ID
([Enable access logs](https://docs.aws.amazon.com/elasticloadbalancing/latest/classic/enable-access-logs.html#attach-bucket-policy),
as cited by the provider on 2026-09-22). A module that copied a table of those
IDs in 2020 is quietly wrong in every region added since, and without a dated
source nobody can tell. The provider has carried
`data "aws_elb_service_account"` throughout, which returns the ID and the ARN for
the configured region. Where a data source exists, deriving the value is the real
fix and this rule is moot - see
[ARNs and partitions](#arns-and-partitions). This rule is for what is left over
after that.

Not in scope, because these are derived rather than copied: a value the module
computes, one from a `data` source, one a variable carries, and a policy the
module builds from its own inputs. There the provider or the data source is the
source.

Also not in scope: a value written inside a comment to illustrate a format or a
conversion. `terraform-aws-s3-bucket` has one -
`modules/notification/main.tf` explains a queue URL conversion by showing
`arn:aws:sqs:eu-west-1:835367859851:bold-starling-0` - and it is an example, not
a constant the module uses. Only a value the code actually evaluates counts,
here and in [ARNs and partitions](#arns-and-partitions).

### Regional availability in an example

An example demonstrating a service or feature that is unavailable in some
regions, for all or most accounts, says so in a comment: which regions, and what
a reader in one of them does instead.

This is not about a service that lags a region or two. It covers the case where
picking a different region produces a failure rather than a delay:

- A service absent from whole partitions, or from the China and GovCloud regions.
- A feature that exists only in a named subset of regions.
- A resource that has to live in `us-east-1` whatever the rest of the
  configuration does.
- Anything gated behind a request or an allowlist rather than open to every
  account.

That comment is a claim about a service limitation, so the standard above applies
to it in full. It is the same rule, not a second one.

Where the example's own region is one the feature does not exist in, the example
is broken, which is a different and more serious thing.

## ARNs and partitions

An ARN the module constructs uses the partition the account is actually in.

The construct already exists and is not invented here.
[module-structure.md](../../references/module-structure.md#locals-pattern)
defines `data "aws_partition" "current"` and `local.partition`, and
[templates/iam.tf.template](templates/iam.tf.template) already builds
`arn:${local.partition}:logs:${local.region}:${local.account_id}:log-group:*`
from it. New code does the same.

`arn:aws:` written by hand is wrong in GovCloud, where the partition is
`aws-us-gov`, and in China, where it is `aws-cn`. A hard-coded account ID or
region inside an ARN the module builds is the same defect one field over.

This too is the family's existing practice. Measured on 2026-09-22,
`terraform-aws-s3-bucket` has no literal `arn:aws:` in its module code at all:
`modules/notification/main.tf` declares `data "aws_partition" "this"` and builds
its bucket ARN as `coalesce(var.bucket_arn, "arn:${data.aws_partition.this.partition}:s3:::${var.bucket}")`.

Two ways to satisfy this, and the second is what keeps it from being overreach:

- Derive it. A `data` source, `local.partition`, or an input the caller supplies.
- Keep the literal, and say in a comment that the value differs by partition and
  which partitions it is right for. Some ARNs genuinely are commercial-only, a
  service with no GovCloud presence being the obvious case. That comment is a
  claim about a service limitation, so
  [Evidence](#evidence-comments-copied-values-and-availability) applies: it
  carries its source and its date.

## Validation

A `validation` block checks its own variable against something the module can
know. Three ways it overreaches.

**It depends on another variable, or on how the module will be used.** A
cross-field invariant belongs in a `lifecycle` `precondition`, which
[module-structure.md](../../references/module-structure.md#preconditions-for-cross-field-invariants)
already says. There is a second reason beyond style: a `validation` that
references anything outside its own variable needs a Terraform version above this
profile's `1.5.7` floor, so [Version floors](#version-floors) applies to it. Look
the introducing version up and check it against the declared floor rather than
assuming it.

**It encodes a compliance or policy judgement.** Requiring encryption to be on,
refusing a public ACL, forcing a retention period, demanding a tag. A reusable
module does not know the caller's context, a `validation` has no escape hatch,
and a caller with a legitimate reason is simply stuck with no way forward. That
control belongs to the caller's policy layer - an SCP, AWS Config, a policy
engine in CI - which can carry an exception. The module's job is to make the
secure configuration reachable and the default sensible.

**It re-implements a service-side naming or format rule whose real constraints
vary.** S3 bucket naming is the case that proves it
([Bucket naming rules](https://docs.aws.amazon.com/AmazonS3/latest/userguide/bucketnamingrules.html),
read 2026-09-22): the rules differ by partition, buckets created before a cutoff
date are grandfathered under looser ones, and directory buckets carry a suffix
format of their own. Any single regex is wrong for somebody, and the person it is
wrong for cannot proceed. The same shape covers IAM name paths, ARNs, and
anything whose format the vendor may extend. The provider or the API rejects
these already, with the service's own message, which is the right place for the
rejection.

A resource name is such a rule too. A `validation` that checks a name's length,
its character set or its first character re-implements the service's naming rule
and overreaches, whether or not that rule is known to vary today, and whether or
not the provider's documentation page repeats it. The list below keeps a bound
the provider schema declares: that is a numeric range on a numeric argument, such
as a retention period in days, and never a pattern on a string.

What a module still validates, so this does not delete useful checks:

- A closed value set the module itself branches on. A mode, an enum, a type name.
  [module-structure.md](../../references/module-structure.md#validation-rules)
  asks for it and this changes nothing there. One rule requires the enum check;
  this one bans everything past it.
- A bound the provider schema itself declares.
- A `precondition` expressing a cross-field invariant, which is the correct home
  for the first case above.

## Example sizing

An example provisions the smallest instance class, capacity, node count or tier
that demonstrates the feature.

In scope are the settings that carry a per-hour price: EC2 instance types, RDS
and ElastiCache instance classes, OpenSearch and MSK node types, provisioned
capacity, node and shard counts, NAT gateways, and a provisioned or reserved
throughput setting where on-demand would do.

Plenty of features do have a floor. Multi-AZ, an instance class that supports a
given engine version, a minimum node count for a quorum, Graviton for something
offered only there. Those are fine, and a comment naming what forces the size is
what makes them fine: it tells the reader the size is deliberate rather than
copied from a production configuration. The convention is against an unexplained
large size, not against a large size.

The cost of getting this wrong lands on two people who did not choose it: the
reader who applies the example to understand the module, and the module's own CI,
which pays it on every run.

## Pull request title and the reason for a break

Two conventions that live with the pull request rather than the code, recorded
here so the set is complete. Their text is elsewhere.

**The title names what changed.** Its shape - Conventional Commit, an accepted
type, an uppercase description - is
[Release and commit conventions](PROFILE.md#release-and-commit-conventions). Its
content is there too: the description names the capability or the fix, and the
surface it lands on when the change is not to the root module. The title
squash-merges into the commit message and from there into the generated
`CHANGELOG.md`, so `feat: Update module` is what a reader finds two years later.

**A break says why compatibility could not be held.**
[pr-description.md](pr-description.md#3-breaking-changes) asks for it: what was
tried, and what the compatible alternative would have cost the consumer or made
impossible. "The provider removed the attribute" is a reason. "The new shape is
cleaner" is not.

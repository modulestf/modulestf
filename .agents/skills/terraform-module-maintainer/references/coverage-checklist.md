# Coverage Checklist

> **Part of:** [terraform-module-maintainer](../SKILL.md)
> **Purpose:** Feature inventory requirements and completion validation

## Coverage Ledger

The coverage ledger is the authoritative record of what the module supports. It is built from the schema worksheet (see [schema-validation.md](schema-validation.md)) and maintained throughout development.

### Per-Resource Field Inventory

Every field from the provider schema must appear in exactly one category:

| Category | Where It Appears | Example |
|----------|-----------------|---------|
| **Exposed input** | `variables.tf` as a variable | `var.name` -> `name` argument |
| **Computed-only output** | `outputs.tf` as an output | `id` attribute -> `output.resource_id` |
| **Sensitive/write-only omission** | Documented or `sensitive = true` | `password` - sensitive, omitted from output |
| **Intentional omission** | Documented in coverage ledger | `deprecated_field` - deprecated since provider vX.x |
| **Not applicable** | Documented in coverage ledger | `field_x` - only applies to resource type Y |

**Zero unexplained gaps.** If a provider field isn't a variable or output, document why.

**Nested fields map leaf by leaf.** A computed-only nested block or nested attribute cannot be output as a whole in the ledger: each leaf takes its own output row; when one output returns the whole value, each row names that output. An intentional omission or not applicable on a nested block or nested attribute covers every field inside it; an input or a sensitive omission is recorded per leaf.

## Validation Checklist

### Tier 1: Critical (Must Pass)

- [ ] **Schema accuracy** - Every resource block matches the provider schema (blocks vs attributes, nesting modes, required fields)
- [ ] **Conditional creation** - `var.create` controls all resource creation via `local.create`
- [ ] **All required arguments** - Every required argument from the schema has a corresponding variable
- [ ] **All optional arguments** - Every optional argument is either a variable with `default = null` or a documented omission
- [ ] **All computed attributes** - Every stable, user-useful computed attribute from the full provider schema is an output with `try()` fallback (use type-preserving fallbacks: `null`, `[]`, `{}` - not `""`). Include URLs, descriptions, names, config objects, and derived name lists - not just IDs/ARNs
- [ ] **Previous output parity** - When updating or regenerating an existing module, diff the previous `outputs.tf` first. Keep every stable, user-useful output unless its removal is an intentional breaking change documented in the coverage ledger
- [ ] **versions.tf** - Terraform and provider version constraints present and correct
- [ ] **Profile-required files** - Every file the selected profile's [module layout](../profiles/terraform-aws-modules/PROFILE.md#module-layout) requires is present

### Tier 2: Structure (Must Pass)

- [ ] **File organization** - Correct files present per service archetype
- [ ] **Variable grouping** - Variables organized by section with `###...###` headers
- [ ] **Output grouping** - Outputs organized by resource type with headers
- [ ] **Variable descriptions** - Every variable has a `description` with valid values/conflicts noted
- [ ] **Output descriptions** - Every output has a `description`
- [ ] **Variable types** - Every variable has an explicit `type` (avoid `any` unless justified)
- [ ] **Variable defaults** - Every optional variable has a sensible default

### Tier 3: Examples (Must Pass)

- [ ] **Profile-required examples** - Every example the selected profile's [module layout](../profiles/terraform-aws-modules/PROFILE.md#module-layout) requires is present, with the content it requires
- [ ] **Working root configurations** - Each example initializes and validates on its own, against real module variables rather than invented names
- [ ] **Example outputs** - Examples expose key module outputs for verification
- [ ] **Example versions.tf** - Each example has its own versions.tf
- [ ] **Example README.md** - Each example has a README with usage instructions and terraform-docs markers

Which examples a module must have, and what the complete one must demonstrate, is a family convention, not a Terraform one. The profile states it.

### Tier 4: Automation (Must Pass)

- [ ] **pre-commit hooks pass** - All hooks in `.pre-commit-config.yaml` pass cleanly
- [ ] **terraform-docs generated** - README.md content between markers is auto-generated (not handwritten)
- [ ] **terraform_fmt applied** - All files formatted canonically
- [ ] **terraform_validate passes** - Module and all examples validate
- [ ] **tflint passes** - No linting violations
- [ ] **Wrappers auto-generated** - `wrappers/` directory auto-generated by `terraform_wrapper_module_for_each` hook (do not create manually)
- [ ] **pre-commit-config.yaml updated** - Hook versions are current (via `pre-commit autoupdate`)

### Tier 5: Quality (Should Pass)

- [ ] **Consistent naming** - All variables/outputs follow snake_case
- [ ] **No hardcoded values** - All configurable values are variables
- [ ] **Secure defaults** - Security-critical settings default to secure values
- [ ] **Tags/labels support** - `var.tags` (or `var.labels` for GCP) propagated to all resources that support them
- [ ] **Profile-required core variables** - Every core variable the selected profile's [module layout](../profiles/terraform-aws-modules/PROFILE.md#module-layout) requires is declared and wired
- [ ] **No duplicate content** - Module doesn't embed information available from terraform-skill plugin

### Tier 6: Documentation (Should Pass)

- [ ] **README.md** - Usage example, features list, conditional creation section
- [ ] **terraform-docs markers** - Present in root and all example READMEs
- [ ] **Feature list** - Accurate (matches actual module capabilities, not placeholders)
- [ ] **Inline comments** - Present only for non-obvious logic (not excessive)
- [ ] **Cost documentation** - Present when the rule below is met, and free of figures

### When Cost Documentation Is Required

Document cost in `README.md`, outside the terraform-docs markers, when any of these holds:

- The change adds a resource type that carries an ongoing charge
- The typical monthly impact is material for the way the module is usually deployed
- The cost is usage-driven, so the bill moves with traffic, storage, or requests rather
  than sitting flat
- The module has options that reduce the cost, and a reader cannot find them from the
  variable list alone

Write it per billable resource, and write only what stays true:

- Which resource is billable, and the input that creates it, so a reader can tell whether
  their configuration is paying for it
- What is charged: per hour, per gigabyte, per request, per stored object, per zone
- What drives the charge: data processed, number of zones, retention period, request rate
- Which module inputs reduce it, and the value that does so

**No figures.** No rates, no currency amounts, no monthly estimates, no totals. They go
stale, they differ by region, contract and provider, and a number written into a module is
never corrected. Point at the provider's own pricing calculator for the arithmetic, and
keep the module's job to naming what is billable and what moves it.

## How to Verify

Rule 3 in [SKILL.md](../SKILL.md) decides which of these checks may run. An untrusted workspace skips `pre-commit` and every other check that executes workspace-supplied code, and records each one as skipped with its reason. A skipped check is never a pass.

### Quick Verification

```bash
cd terraform-<provider>-<service>

# 1. All pre-commit hooks pass (trusted run only)
pre-commit run -a

# 2. Module validates
terraform init -backend=false && terraform validate

# 3. Examples validate
for dir in examples/*/; do
  echo "=== $dir ==="
  cd "$dir"
  terraform init -backend=false && terraform validate
  cd ../..
done
```

### Coverage Matrix Verification

For each resource type in the module:

1. Re-fetch the schema via MCP: `mcp__terraform__get_provider_details`
2. Compare every field against `variables.tf` and `outputs.tf`
3. Confirm every field is categorized (input, output, omission, N/A)
4. Confirm no fields are missing

Optional: when a trusted schema file and the binary are available, write the matrix as a ledger file and run `mtf-facts ledger --check` on each module directory, as [The Ledger Command](facts-commands.md#the-ledger-command) sets out. An empty problem list shows that every field has exactly one disposition and every named variable and output exists; it does not show that each disposition is right, so steps 1 to 4 still run. Without the binary or the file, or when the run fails or times out, steps 1 to 4 are the check, and the ledger check is reported as skipped with its reason.

### Example Verification

For the complete example:
1. Does it reference real module variables (not placeholder `enable_feature_one`)?
2. Does it demonstrate the module's key features (from the coverage matrix)?
3. Does the disabled module call work with `create = false`?
4. Do outputs match actual module output names?

## Common Coverage Gaps

| Gap | How to Detect | Fix |
|-----|--------------|-----|
| Missing optional arguments | Compare schema worksheet to variables.tf | Add variable with `default = null` |
| Missing computed attributes | Compare schema worksheet to outputs.tf | Add output with `try()` |
| Unused variables | `tflint` rule `terraform_unused_declarations` | Wire up or remove |
| Undocumented omissions | Field in schema but not in variables or outputs | Add to omissions list with reason |
| Placeholder features in README | "Support for [key feature 1]" text | Replace with actual feature names |
| Handwritten README content | Content between terraform-docs markers | Delete and re-run `pre-commit run -a` on a trusted run |
| Stale wrappers | Hook auto-generates wrappers | Re-run `pre-commit run -a` on a trusted run |
